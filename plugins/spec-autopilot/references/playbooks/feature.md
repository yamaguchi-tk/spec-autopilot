# playbook: feature（機能を足す・変える）

選ぶとき: 新しい機能・画面・CLI・API を足すか、既存の機能の振る舞いを変える spec。

## spec を書くとき（A・B）

- 推奨で埋める草案には、依頼の目的に加えて、**その種類のものに普通は付く機能と既定値**を推奨の要件として入れる（ゲームなら最高点の保存・使う画面に合う大きさ、CLI なら CI 向けの検査オプション・よく使われる既定の範囲など）。ただし大きさ S の草案では、次の S の項の目安に収まる範囲に絞る
- 既定は、人が見て違うと言える値で書く（大きさ・速さ・範囲・件数など。大きさは使う場面の画面に対する割合で）。人は値を見ないと反応できない（計測では、大きさを書かない草案に、違う大きさを望む人が何も言わずに OK を返した）
- 画面やメッセージの文言は依頼の言語にする
- 人は試作が薄くても承認しがちで、口に出さなかった要望は既定でしか拾えない（計測では、口に出さなかった要望の充足は、最小の要件にしたハーネスが 17/29、素の Claude Code が 15/19 だった）
- 表の要件の数を超えない（S なら 12 個まで）。凝った機能（効果音・オンライン対戦・テーマの切り替えなど）だけを非目標の節に「足すなら」として 1 行ずつ挙げる
- 大きさ S の草案は、要件を全部満たす本体（テストと docs を除く、足す行）が 200 行に収まる中身にする。数は上限の 12 個まで埋めず、収まる分だけにする。その種類の公式のルールや資料の細部（ゲームなら回転の補正の表・固定の猶予の回数・落下の速さの式など）は要件に入れず、非目標の「足すなら」に挙げる（計測では、「シンプル」と頼んでも要件が上限の 12 個まで埋まり、本体が目安の 1.7 倍の 342 行になった）。その種類のものに普通は付く機能（最高点の保存・画面に合う大きさなど）は、目安に収まる範囲で残す。収まらないなら、非目標へ移すか、大きさを M にする
- 既存の repo では、影響範囲・変えない挙動を `references/existing-repo.md` のとおりに書く（種類によらず lint が求める）

## 自走のタスク（A の 0 で選んだらすぐ tasks.md の先頭に写す）

- 種類に固有のタスクは無い。要件ごとに、触るファイルのまとまりで分ける

## 評価役の観点

- 種類に固有の観点は無い。変更の性質で決まる観点（権限・認証、本番に直接効く）は `commands/autopilot.md` の C の 3 で選ぶ
