# playbook: external-service（外部サービスを呼ぶ）

選ぶとき: AWS・Slack・LLM の API など、repo の外のサービスを呼ぶ・応答で分岐する要件がある spec（feature・bug-fix と並べて書いてよい）。

## spec を書くとき（A・B）

- QA の方向性の確かめ方に、本物で確かめる手順を書く（test チャネルへの投稿、本物の LLM を何回か走らせる、対象のアカウントでの読み取りなど。書き込むのは「## 自走の範囲」の QA の書き込み先だけ）
- 単体テストでは代役（moto・botocore の Stubber・クライアントの差し替えなど）を使ってよい。本物で確かめられない部分だけ、合格基準に「unverified（<理由>）」と書き、`- unverified の承認: R<n>（<理由>）` を添える（手戻りの 8 本は、どれも手元のテストと評価役を通り、実環境で初めて出た欠陥だった）
- エラーコードや応答で分岐する要件は、同じコードが返るほかの場合を公式の文書で調べ、区別する条件を要件に書く（計測では、「組織に無い account」を `AccountNotFoundException` だけで判定し、呼び出す側が組織のメンバーでないときも同じ例外が返ることに、どの回も気づかなかった）
- Slack に投稿する・表示を変える要件は、合格基準に、test チャネルで見た表示（崩れ・文字数の上限・mrkdwn の効き方）を書く

## 自走のタスク（A の 0 で選んだらすぐ tasks.md の先頭に写す）

- 種類に固有のタスクは無い。本物での確かめは評価役が QA の方向性のとおりに行う

## 評価役の観点

- Slack の表示と書き込み先（Slack に投稿する・表示を変えるときだけ）
