# playbook: refactor（挙動を変えずに構造を直す）

選ぶとき: 利用者から見える挙動を変えずに、コードの構造（結合度・凝集度・複雑さ・重複・ファイルや関数の大きさ）を直す spec。ファイルの分割・関数の切り出し・依存の整理など。

## spec を書くとき（A・B）

- 書く前に、変える前の指標の値を実物で測る。測ったコマンドと結果を「## 前提」の `- 前提:` の下に `  - コマンド: `<cmd>` → <結果>` で書く。測るコマンドは「指標を測る道具のコマンド」と書き、特定の道具の名前とパスを書かない（道具は repo の外にあり、plugin を入れたほかの人は同じ道具を持たない。書く人が自分の道具で測る）。測れないなら `  - 未確認: <理由>` と書き、推測の値を書かない
- 指標は、直したい構造に合うものを選ぶ。行数だけを指標にしない（移しただけでも減る）。例: 複雑さ（循環的複雑度・認知的複雑度）、結合度（依存の数・循環した依存）、凝集度（1 つの単位が持つ責務の数）、重複、関数・ファイルの大きさ。狙う指標とその目標の値を要件に書く
- QA の方向性の合格基準は「指標の前後の比べ方で悪化が無く、狙った指標が目標の値に届き、移しただけでない」の形で書く。段は `手元で実物`。「悪化が無い」は、前提に書いた指標ごとに、変えた後の値が前以下であることを指す
- 「挙動を変えない」ことを要件にし、「## 変えない挙動」に既存のテストの名前を書く。テストが無い箇所を直すなら、先にその挙動を固定するテストを足すことも要件に入れる
- 要件は「<指標>が<前の値>から<目標の値>に届く。」「既存のテストが変わらず通る。」の形で、値と比べ方を条件にする

## 自走のタスク（A の 0 で選んだらすぐ tasks.md の先頭に写す）

- [ ] T1: 指標を測る道具のコマンドで、変える前の値を測り、コマンドと結果を記録する [R<n>]
  - メモ: 前提に書いた値と合うことを確かめる。合わなければ、前提を測った値に直す
- [ ] T2: 構造を直す [R<n>]
  - メモ: 既存のテストを書き換えて通さない。挙動を固定するテストを足すなら、先に足して通ることを確かめてから直す
- [ ] T3: 変えた後の値を同じコマンドで測り、前の値と比べる [R<n>]
  - メモ: 指標ごとに前と後を並べて書く。悪化したもの、目標に届かないものは、そのまま報告に書く

## 評価役の観点

- 移しただけで複雑さが変わっていないか（行や関数を別のファイルや別の名前へ動かしただけで、分岐の数・依存の数・責務の数が前と同じか増えていないか。指標の前後を同じコマンドで測り直して比べる）
- 狙わなかった指標が悪化していないか（前提に書いた指標の全部を測り直す）
