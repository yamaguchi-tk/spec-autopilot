# playbook: bug-fix（不具合を直す）

選ぶとき: 既存の振る舞いが期待と違う、エラーが出る、などを直す spec。

## spec を書くとき（A・B）

- 書く前に実物で再現する。再現の手順と結果を「## 前提」の `- 前提:` の下に `  - コマンド: `<cmd>` → <結果>` で書く（再現できないなら `  - 未確認: <理由>`。推測で原因を書かない）
- 要件は「<再現の手順>のとき、<対象>は<期待の応答>する。」の形で、再現の手順をそのまま条件にする。QA の方向性の段は再現した面と同じ段（既定は `手元で実物`。本番でしか再現しないなら `デプロイ後`）、合格基準は「base で落ち、tip で通る」
- 根本の原因を直す要件にする。正当でない状態を握りつぶすガード（`if x is None: return` など）を要件にしない（バグを隠す）
- 「外部の原因」（AWS・ライブラリ・相手のサービス）と結論するなら、その根拠（ログ・公式の文書・再現）を前提の確かめ方に入れる
- 同じ種類の不具合が再び出たら気づける常時の信号（CloudWatch のアラームなど）を、推奨の要件として草案に入れる（人が外せる。done の報告では出さない）
- AWS を読む・操作する spec は、「## 自走の範囲」の `- AWS の profile:` を対象のアカウントのものにし、`aws sts get-caller-identity` の結果を前提に書く（プロファイルの取り違えで別のアカウントを調べた事例がある）

## 自走のタスク（A の 0 で選んだらすぐ tasks.md の先頭に写す）

- [ ] T1: 再現の手順を、落ちる自動テストにして先に commit する [R<n>]
  - メモ: base で落ちることを確かめてから commit する
- [ ] T2: 根本の原因を直す [R<n>]
  - メモ: 否定された仮説から足したコードは戻す
- [ ] T3: 同じ種類の箇所を洗い出し、同じ直しを当てる（当てないなら理由をメモに書く） [R<n>]

- 同じ種類の箇所
