# 行き詰まりの手順

合意の後に行き詰まっても、人に聞かない。段と回数はこの文書が正本で、`autopilot.py` が要件ごとに数えて `check`（と Stop hook）で強制する。

数えるのは、実装が終わったと言った後に、ある要件の検証が落ちたこと。記録は `autopilot.py fail <dir> --req R<n> --from impl|qa --evidence ...`（implementer が満たせなかったと報告した・QA が fail）と、`autopilot.py review <dir> --high R<n>,...`（最後のレビューの high）で行う。TDD の途中の red と、check の進み具合の誤り（タスクが終わっていないなど）は数えない。数える単位はレビューの巡（`review` の記録から次の `review` まで）。巡の中でその要件に失敗か high が 1 つでもあれば +1（何件あっても 1 回）、無ければ 0 に戻す。3 巡に届いた要件は、作り直す（rework）まで 0 に戻さない。失敗の記録そのものは消さない。

## 1. 同じ要件の失敗が 2 巡続いたら: 原因を調べる

推測で直さない（この巡で、`CLI review` が実装役の段をその要件について 1 段上げる。その巡に `CLI fail --from impl` でもう上げ、上げた段をまだ渡していなければ上げない。`commands/autopilot.md` の C の 3）。失敗を再現して出力を読み、直しの案より先に、次の順で前提を確かめる。

1. 落ちた 2 巡の直しが頼っていた前提を書き出す（「この文を強めれば、その順に読まれる」「この関数にこの形の入力が来る」など）。前提ごとに、確かめる場所（出力・コード・定義の path:line）を 1 つ書く
2. 前提を 1 つずつ、書いた場所で確かめる。崩れた前提があれば、それを根本の原因とし、その前提に頼らない直しを選ぶ
3. 前提が全部成り立つときだけ、仮説を 1 つ立てて確かめる
4. 確かめた前提と結果は、tasks.md の該当タスクの下に `  - メモ: 前提: <前提> → <成り立つ|崩れた>（<確かめた場所>）` の行で残し、実装役に渡す（後で下の「## 2.」の作り直し〔`autopilot.py rework`〕で tasks.md を直すときも、この行は消さない）

ガード（例外の文・特別扱いの分岐・入力を弾く条件）を足す直しは、ガードが守る状態がそもそも正しいときだけ、根本の直しに数える。前の巡の直しを強めるだけの直し（同じ例外の文を言い換える、条件を 1 つ足す）は、上の手順の 1〜2 で前提が全部成り立つと確かめたときだけ選ぶ（崩れた前提に頼る強め方は選ばない。事例では、失敗が 2 巡続いた後の直しで、照合役の項目 10 の例外の文を強めた。例外の文が表の見出しと一般の規則に負けるという前提を書き出したのは、3 巡続いた後の作り直しのときだった）。根本の原因が分かったら直して進む。

## 2. 3 巡続いたら: 作り方を変える（check が落ちる）

同じ形の修正を続けない。spec に戻る（この巡で、`CLI review` が実装役の段をその要件について 1 段上げる）。

1. 行き詰まりを生んだ前提（選んだライブラリ・データの形・分け方など）を 1 つ挙げる
2. spec の要件と制約をすべて満たす別の作り方を 2 つ以上挙げる。要件を緩める案は挙げない
3. 選んだ作り方を新しい ADR に書き（前の ADR は `Superseded`）、`autopilot.py rework <dir> --req R<n> --adr <新しい ADR>` で記録して、spec の「作り方」の節と tasks.md を直して進む（作り方の節と、先頭の `- ADR:` 行の番号は承認の検査の対象外。spec 先頭の `- ADR:` の行は、別の ADR に付け替えない。tasks.md を直すときも、1 の手順 4 の `  - メモ: 前提:` の行は消さない）。rework はその要件の巡の数を 0 に戻す

ADR には、直し方の段と、それより上の段を退けた理由を書く。段は上から、要らなくする・入力の約束を変える・設計を変える・局所の継ぎ足し。選んだ段より上の段ごとに、退けた行を 1 本ずつ書く。理由が要件の文なら `- 要件の文で退けた:` の形を使う。rework は行の有無と形だけを見て、足りなければ記録しない。

```
- 直し方: <段>
- 退けた: <段>（<理由>）
- 要件の文で退けた: <段>（R<n> の「<要件の語>」）
```

「要件の文で退けた」の行が 1 本でもあれば、rework は記録せず、行ごとに `overnight.py park ... --req R<n>` のコマンドを出す。そのまま打って、その要件を park に積む（人が朝の報告で要件の文を直すかを決める）。

作り直しは 1 つの要件につき 2 回まで。3 回目の rework は CLI が拒む。

## 3. 積む（park）: その要件だけが進められないとき

夜の間は返事が来ないので、1 つの要件のために全体を止めない。次のどれかに当たった要件は、`overnight.py park <dir> --kind <merge|deploy|qa|ci|other> --op "<要る操作>" --reason "<理由と証拠>" --req R<n>` で積み、qa.md のその要件の行を `unverified（park: <理由>）` にして、ほかの要件を進める。積んだものは朝の報告の先頭に出る。

- 実装役の段の梯子の一番上（Fable を 1 回）でも通らない（review・dispatch が park を言う）
- 作り直しの ADR に `- 要件の文で退けた:` の行があり、rework が拒んだ（出たコマンドで積む）
- 作り直しを 2 回しても、その要件を満たす作り方が見つからない（マージの後のデプロイ後の要件なら、積む前に `references/after-pr.md` の 5 で本番を戻す）
- その要件を満たすには、承認した「## 自走の範囲」の外の操作が要る（agent が自分で打つ `terraform apply`、範囲に無い環境への書き込みなど。実行しない）
- 評価役が `原因: 差分の外` の fail（認証・権限・backend が無いなど）か、IaC の QA の方向性の不足（対象のアカウントでの plan が無い）を返した
- デプロイの失敗を直す PR が 2 回とも通らなかった（`references/after-pr.md` の 3。戻さずに積む）
- branch protection・必須レビューでマージを断られた（`--admin`・`--auto`・`gh api`・直接の push で回避しない）、3 回目の rebase が要る、機械の待ちが上限を過ぎた（`references/after-pr.md`）

## 4. 人に戻る（block）: どの要件も進められないとき

次のどれかに当たったときだけ、`autopilot.py block` で記録して止まる。

- 積んでいない要件が 1 つも残らず、どれも進められない
- 要件どうしが両立しないと分かった（片方を満たすと、もう片方が満たせない証拠がある）。spec を直す合意し直しが要る
- 予算の 2 倍を過ぎても完了の検査が通らない（Stop hook が知らせる。マージの後は、マージ後の予算をマージの時刻から数える）。予算は spec の制約なので、制約を満たせないものとして示す

判断に迷うこと、レビューの low が残っていること、ブラウザの tool が無いことは、止まる理由にしない。
