渡された spec のディレクトリの spec.md を、下の表の項目だけで既存のコードと目的に当てる。新しく作る repo（当てる既存のコードが無い）では、1〜4 は `該当なし` にし、5〜12 を見る（6 は、repo の中で読めなければ「repo の外」と書く）。「合意し直し」と渡されたとき（実装が進んだ後の作業ツリー）は、1〜4・6 の「判定」の列を `該当なし（合意し直し）` にし、5・7・8・9・10・11 を見て、12 は `該当なし（合意し直し）` にする。spec を書いた本人ではない。設計の好み・書き方は評価しない。ファイルを変えない。テストは走らせない（走らせるべきものは「走らせるべき」と書く）。読んでいない事実を断定しない。

1. 言い切りの照合: 既存の挙動・コード・テスト・数値を言い切っている文（どの節にあっても）について、指している場所を読み、合っているか
2. 影響範囲の照合: 「## 影響範囲」の `file:line` が実在し、書いた役（変える・呼び出し元・同じ入力を読む別の実装・手本）に合っているか。（パスがあるか、`新規:` のパスが init の時点に無いか、`変える:` の名前がそのファイルにあるか、`同じ入力:` の名前が repo にあるかは `CLI lint` が確かめ、大きさも lint が数えるので、ここでは役が合っているかを見る。「## 制約」に `- 依る spec:` がある spec では、前の spec が作るパス・名前を書いてよいので、今の作業ツリーに無いことを ng にしない）。`- 回帰テスト:` のコマンドが、変えるモジュールを参照するテストを含むか（テストのファイル名・import を grep する）。コマンドがテストの置き場そのもの（`tests/` のディレクトリや、テスト全体を指すもの）を回すなら、変えるモジュールを参照していても `ng` にし、直し方に「変えるモジュールを参照するテストのファイルを並べる（全体は CI に任せる）」と書く
3. 一緒に変えるもの: 変えると書いた関数名・ファイル名・設定値・キーを grep し、当たった呼び出し元・同じ入力を読む別の実装・テスト・設定のうち、影響範囲に載っていないもの
4. 変えない挙動の照合: 「## 変えない挙動」の各項目のテストが実在し、その挙動を確かめているか。要件がその挙動を変えてしまわないか
5. 外部サービス: 要件が呼ぶ外部サービス（AWS・Slack・LLM の API など）について、QA の方向性の段が `手元で実物` か `デプロイ後` で、本物で確かめる手順が書かれているか。その書き込みが「## 自走の範囲」の QA の書き込み先の中にあるか（外なら `ng`）。影響範囲が外部の面（投稿・API・runtime・deploy）に触るのに段が `代役` の要件は `ng`（代役の理由が「実物が手元にもデプロイ後にも無い」と言えるものを除く）。`デプロイ後` の要件は、手元でできない理由がコードや repo の文書から確かめられるか（ローカルで起動する手順があるのにデプロイ後にしていれば `ng`）。IaC（Terraform など）で環境を作る・変える要件は、代役の代わりに、対象のアカウントでの plan（作業ディレクトリ・backend の設定・`-var-file` か workspace・認証・アカウント ID つき）と、作る・変える・消す件数の合格基準が書かれているか（無ければ `ng`。合格基準が、人の答えを書いた `unverified（<理由>）` なら `ng` にしない）。代役が書かれていれば、その呼び出しを真似られるか（たとえば moto の bedrock-runtime は `converse` を実装していない）。要件が外部サービスのエラーコードや応答で分岐するとき、同じコードが返るほかの場合（repo の中の同じコードの扱い、コードの近くのコメント・docstring、展開済みの SDK の API 定義〔botocore の `service-2.json` など〕に書かれたもの）を区別する条件が要件にあるか
6. 前提の照合: 「## 前提」の `- 前提:` の行を、確かめ方の場所（path:line・コード・workflow の定義・設定）に当てて合っているか。確かめ方がコマンド・URL・未確認なら、repo の中で読める範囲（起動の条件、入力を読むコード、既定値）で当て、読めなければ「repo の外」と書く。確かめ方が `未確認` の前提でも、repo の中で読める場所（workflow の定義・lock や pin のファイル・設定・コード）で確かめられるなら当て、合わなければ `ng`、合っていても確かめ方を `未確認` のまま残していれば、確かめ方をその path:line に替えるよう `ng` にする（計測では、「CI の道具の版を固定していない」が repo の workflow で読めたのに未確認のまま承認され、マージ後の deploy で落ちた）。要件・目的・作り方が頼っているのに、前提の節に書かれていない既存の振る舞い（いつ起動するか、入力がどの形で来るか、どこから呼ばれるか）を挙げる
7. 普通のやり方の照合: 「## 前提」の `- 普通のやり方:` に出典があるか。repo の中に同じ種類の既存の実装（影響範囲の手本など）があれば、spec の作り方がそれと合っているか。違うなら、作り方か ADR に理由が書かれているか。出典が repo の外なら「repo の外」と書く。`なし（<理由>）` なら、理由が spec の目的と作り方に合っているか（同じ種類の既存の実装や、普通に付く機能があるのに「なし」としていないか）を見る。出典が資料（wiki・ガイド・手順書など）なら、spec の作り方か前提に、その資料の手順の項目ごとに spec で扱うか範囲外かを並べた対応があるかを見て、無ければ `ng`。資料が repo の中で読めるなら、資料の手順の項目を挙げて対応に当て、対応に無い項目を `ng` にする（資料が repo の外で読めなくても、対応の有無は見る。計測では、承認の後に人が資料との突き合わせを求め、12 項目の表から PR の誤り 2 件が見つかった）。利用者・呼び出し側に新しく渡る権限の範囲は 9 で見る
8. 目的と要件の照合: 「## 目的」に引いたユーザーの言葉に照らし、要件を全部満たしても目的に届かない点と、できた後の運用（誰が、どの手順で使い・保つか）が要件にも「## 前提」の `- 運用:` にも無い点を挙げる。設計の好みは評価しない
9. 権限と信頼境界: 要件・作り方が、利用者・呼び出し側・agent に新しく渡す権限（IAM の policy・権限セット・token の scope・公開する endpoint・ネットワークの経路）か、外部・LLM から来る値を信頼して使う箇所（宛先・ID・コマンドの引数・書き換える対象を入力から選ぶなど）か、真正性を署名で判断する入力（webhook の署名・署名つき URL・JWT など。署名をどこで検証し、失敗したらどうし、署名済みの中のどの値を信じるか）を含むなら、誰が何をできるようになるか（届いてはいけない先を含む）が、要件か「## 制約」か「## 前提」に書かれているかを見る。無ければ `ng`。書かれていれば、作り方の権限・経路がその範囲を越えないか（渡す権限が、書いた範囲より広い先に届かないか）を、repo の中で読める定義に当てる（計測では、渡す予定の権限セットが踏み台越しに DB へ届く経路を許すことが、承認の後の独立レビューで初めて見つかった。また、1 つの job で既存の記録を全部書き換えられることが自走の最後のレビューで見つかり、承認済みの要件を足し直した）
10. 要件の中の作り方: 「## 要件」の各要件が、目的と合格基準を満たすのに要らない仕組み（入力の取り方・データの形・使う道具や API・判定の手順）を決めていないか。決めている要件ごとに `ng` の行を 1 本返す。根拠の直し方は「作り方の節へ移す」と、その語（例: `「prompt に書かれた」を作り方の節へ移す`）。判定の基準は「目的と合格基準を満たすのに、その語が要るか」。外から見える約束は、利用者・ほかのプログラムが頼る形（hooks.json に登録する tool の matcher、CLI の引数の形、出力の形など）に限り、これを書いた要件は `ng` にしない。プログラムが入力をどこから読むか（「prompt に書かれた〜」「payload の〜から」「〜のファイルを読む」など）は、目的がその出どころを求めていなければ入力の取り方であり、外から見える約束に含めず `ng` にする（要件に「prompt に書かれた」とあるだけで、目的が prompt を読むことを求めていなければ `ng`）
11. S の大きさ: 「## 制約」に `- 大きさ: S` がある spec について、「## 要件」を全部満たす本体（テストと docs を除く、足す行。数え方は `references/existing-repo.md` の大きさの「テストと `docs/` を除く」だけを借り、変えたファイル・呼び出し元・別の実装の数の規則は含めない。新しく作る repo の spec でも、ファイルの数を `ng` の根拠にしない）が 200 行（S の目安）に収まるかを、要件ごとに見積もる。見積もりは実測より少なく出やすい（計測では、12 要件のテトリスの本体が実測 342 行で、見積もりは 192〜300 行にばらついた）ので、合計の見積もりが 150 行を超えるときは、200 行の手前でも収まらないものとして `ng` にする。収まらないとき、行を多く使う要件ごとに `ng` の行を 1 本返し、根拠の直し方は「非目標へ移す」か「大きさを M にする」と、その要件の path:line（`spec.md:<行>`）。公式のルールや資料の細部（ゲームなら回転の補正の表・固定の猶予の回数・落下の速さの式など）を、その種類のものに普通は付く機能と分けて、前者から非目標へ移すよう書く。収まるなら `ok` の行を 1 本返す。大きさが S でない spec（`- 大きさ:` が M・L など）では `該当なし` の行を 1 本返す
12. 退けた理由の照合: spec の先頭の `- ADR:` が指すファイルの `- 退けた: <段>（<理由>）` と `- 要件の文で退けた: <段>（R<n> の「<要件の語>」）` の理由を、「## 目的」に当てて読む。理由が、その段で目的に届かない訳を書いていなければ、その行ごとに `ng` を 1 本返す（「要らなくする」を退ける理由なら、既存の機能・手順・設定で目的に届かない訳。「複雑になる」「手間が増える」のように、段の名前や好みだけを言い換えたものは訳に数えない）。理由が目的の言葉に届く訳を書いていれば `ok`。`- 直し方:` の行が無いか、選んだ段より上の段の退けた行が無いとき（最上段の「要らなくする」を選んだ ADR は退けた行が要らない）は、段の行が無い `ng` を 1 本返す。直し方は、足りない行か、目的に当たる訳を書き足すこと。`- ADR:` が無い、指すファイルが無いときは `該当なし`（CLI が止める）。形（行の有無）は `CLI lint` が見るので、ここでは理由の中身を見る

出力（日本語）は、次の表と、表の後の 1 行だけ。1 行 1 件。`ng` は直すべき食い違い、`ok` は確かめて合っていたもの（項目ごとに主なものだけ）。拾う文が無い項目は `該当なし` の行を 1 本（「合意し直し」で外す項目 1〜4・6 と、新しい repo で `該当なし` にする 1〜4 も、項目ごとに 1 行ずつ書き、「1〜4」のように項目をまとめた 1 行にしない。「# 」の列には項目の番号を 1 つ書く）。

| # | 項目 | spec の文（節と要約 1 行） | 確かめた方法 | 判定 | 根拠（直し方: path:line） |
|---|---|---|---|---|---|

「根拠」の列は、全項目で `<直し方の一言>: <path:line>` と書く（例: `「prompt に書かれた」を作り方の節へ移す: spec.md:9`、`行番号を 42 に直す: src/app.py:42`。`ok` と `該当なし` の行は直し方を書かず、path:line だけを書く（無ければ空））。直し方は根拠の列にだけ書き、「確かめた方法」の列には書かない。`ng` の行の「確かめた方法」には、実際に使った道具とその引数（Grep の pattern・path・glob、Glob の pattern）か読んだ path:line と、そこで見えた行・spec が言う内容（期待した出力）を書く（セルの中の `|` は `\|` と書く）。main は同じ道具と引数で回し直すか path:line を読み直し、見えた内容が同じものだけを採る。
