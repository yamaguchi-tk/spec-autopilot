# /autopilot

依頼: $ARGUMENTS

この本文の `CLI <sub> ...` は、`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/autopilot.py" <sub> ...` をそのまま実行することを指す（シェル変数に入れない。zsh では分割されない）。`NIGHT <sub> ...`（本文で `overnight.py <sub>` と書くものも）は、同じく `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/overnight.py" <sub> ...` を指す。`lineup.py <sub>` も同じく `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lineup.py" <sub>` を指す。工程は 3 つで、人と話すのは A と B だけ（小さい修正で A・B を省く軽量フローは L）。

| 段 | 人 | 成果物 | 機械の検査 |
|---|---|---|---|
| A 壁打ち | 話す | （まだ無い） | なし |
| B 合意 | 1 回承認する | spec.md・ADR | `CLI lint`（誤りがあれば承認に進めない）→ `CLI approve` |
| C 自走 | 聞かない | tasks.md・コード・テスト・qa.md・PR | `CLI check`。通るまで Stop hook が turn を終えさせない |
| L 軽量フロー | 聞かない（A・B を省く。範囲は spec の `- 範囲:`） | spec.md・ADR と C と同じもの | `light.py approve`→ `CLI check`（保護 path に触れたら止まる） |

ユーザーの CLAUDE.md の安全規則（インフラ操作の 1 操作ごとの確認など）は、この本文より優先する。

## 0. 準備

1. worktree で始める（main・master と、ほかのセッションの checkout で作業しない）。commit のたびに `git show --stat HEAD` で、意図しないファイルが入っていないか確かめる。既存の repo が `docs/specs`・`docs/adr` の下を 1 つも commit していなければ、`CLI init` は追っていない置き場ごとに、中身が `*` の `.gitignore` をその置き場に書き（効くのはその worktree だけ）、commit しないと知らせる。人が最初の 1 本を `git add -f` で入れた repo では、次の init がその `.gitignore` を消す（事例では、spec を commit しない repo の PR に spec・ADR を入れ、人に外させた）。git が無視するファイルは `git add -f` で足さない
2. 既存の repo（docs/specs・docs/adr の外に git が追っているファイルがある）なら、関係するコードと `docs/specs/`・`docs/adr/`・repo の CLAUDE.md、変える場所の過去の取り組み（`git log -- <paths>`、`gh pr list --state all --search <語>` と、そこから辿れる課題・記事。GitHub に無い repo や gh が使えない環境では `git log` だけを読み、`- 過去:` にそう書く）を読んでから話し始める。問いに答えがコードにあるなら聞かない。読むのは、ファイル → クラス・関数 → 行の順に絞り、関係の無いファイルを全文で読み込まない（大きい repo では Explore の subagent に、依頼に関係するファイル・関数・テストの `file:line` を列挙させる。公開の評価では、段階的に絞ると、正解のファイルが候補に入る率が約 8 割で、全文を渡すより安く当たった）
3. `.claude/gdd-dev.local.md` の `active:` が false 以外で、Claude Code の設定（user・project・local の settings.json の `enabledPlugins`）で GDD の plugin が有効なら（user の settings.json は `CLAUDE_CONFIG_DIR` があればその下。読めない設定は有効とみなす。判定は `CLI lint` と同じで、迷ったら `CLI lint` の結果に従う。この判定は user・project・local の settings.json だけを読む。それ以外の経路（`--plugin-dir`・`--setting-sources`・`--settings` など）で GDD が読み込まれていれば、GDD の hook が止めうる。`CLI lint` も ERROR にする）、GDD の hook がこの流れを止める。そう伝え、GDD のタスクを終えるか、この repo で GDD を無効にするかを聞いて止まる。GDD の plugin が有効でなければ、GDD を外した後に残った lock なので止めない（`CLI lint` は NOTE にする）
4. 対象の repo の `.claude/skills/verify-*/SKILL.md`（verify skill。手元で実物を動かして確かめる手順）を探して読む。あれば、QA の方向性の確かめ方・QA の環境・書き込み先の既定をそこから取る。無くて、spec に `手元で実物` か `デプロイ後` の要件が入りそうなら、人がいる間（壁打ちの間）に `templates/verify-skill.md` から作る。test チャネル・書き込み先・アカウントは人に聞いて埋め、雛形の「1 回通し」を通してから使う。作りたての skill で、それを作るきっかけになった spec 自身の QA はしない（skill の誤りと spec の欠陥を見分けられない。その spec は QA の方向性の確かめ方で確かめ、skill は次の spec から使う）。作った skill は spec と別の PR にし、まとめて承認する（B の 5）なら、その先頭に置く。その PR のマージは、壁打ちの間に人が行うか、承認（B の 4）で示して人が承認したときだけ main が行う（どちらも無ければマージせず、その PR を park に積み、朝の報告に出す）

## A. 壁打ち

最初の依頼は、本当に欲しいものを正しく表しているとは限らない。

0. 何を作るかの見当が付いたら、すぐに `CLI init <slug>` を実行する（壁打ちの時間も `done` が「着手から」で測るため）
   - 作業の種類が分かったら、最初の草案より前に playbook を選んで読み、草案の「## 制約」に `- playbook: <名前>[、<名前>]` と書く（`CLI lint` が求める。当たるものが無ければ `- playbook: なし（<理由>）`）。種類に固有の書き方・タスク・評価役の観点は playbook にあり、選んだものだけを読む

     | 名前 | 選ぶとき |
     |---|---|
     | `feature` | 機能・画面・CLI・API を足す、既存の機能の振る舞いを変える |
     | `bug-fix` | 期待と違う振る舞い・エラーを直す |
     | `iac` | Terraform などで資源を作る・変える・消す（権限を絞る変更も） |
     | `external-service` | AWS・Slack・LLM の API など、repo の外のサービスを呼ぶ（ほかと並べて書く。例: `feature、external-service`） |

     置き場は `references/playbooks/<名前>.md`。大きさが S なら、これとは別に `references/small-prototype.md` を読む（試作は大きさで決まり、playbook では選ばない）。選んだら、その playbook の「自走のタスク」のタスクの行をすぐに、言い換えずに tasks.md の先頭に写す（`[R<n>]` は B の 1 で要件を書いた後に埋める）。既存の repo（下の 2 の定義）なら、種類によらず `references/existing-repo.md` も読む
1. 依頼を自分の言葉で言い直し、**なぜ欲しいのか**と、**できあがったら何が変わるのか**を聞く。依頼の言葉どおりに作ると目的を外す点・もっと安い道を見つけたら、はっきり言う。見つけるのを待たず、先に「そもそも要らなくできないか（既存の機能・手順・設定で目的に届かないか）」「入力の約束を変えれば消えないか」を自分に問い、答えを 4 の案に入れる
2. 問いは 1 回に 1 つ。答えで作るものが変わる問いだけを聞く。決められることは推奨として書き、直せる形で示す
   - **最初の返事から、推奨で埋めた spec の草案を示す**（下の 3・4 で決めたことを、先に B の 1〜3 で書いて lint を通してから示す）。問いと一緒に「推奨のままでよければ、この spec の承認として OK と返してください」と添える。人が OK と返したら、それが B の 4 の承認になる。問いに答えや直しが返ったら、spec を直して示し直す。問いが残らないなら、問わずに承認だけを求める
   - 草案を後回しにして問いだけを返すと、承認までに人の返事が 1 往復増える
   - **S では、草案と一緒に動く試作を出す**: 手順は `references/small-prototype.md` に従う（大きさが S のときは必ず読む）
3. 大きさを決める。深さと予算の既定は次のとおり（人が上書きできる。ただし既存の repo では、下の項のとおり数えた大きさより小さくできない。初回の合意では、L は 1 本の spec で合意できない）

   | 大きさ | 例 | 要件の数 | 変更の目安 | 予算（承認から PR まで） | 実装 |
   |---|---|---|---|---|---|
   | S | 1 画面のゲーム、小さい CLI、1 か所の修正 | 〜12 | 〜200 行 | 30 分 | implementer が全要件を 1 本で |
   | M | 画面や API が数個、既存の機能の数か所の変更 | 〜15 | 〜400 行 | 90 分 | タスクごとに implementer（新しく作る repo は、全要件を受け持つタスク 1 つを implementer 1 本で） |
   | L | それより大きい | — | 400 行を超える | 分けた spec ごと | 分けた spec ごとに S か M |

   - L は 1 本の spec にしない。初回の合意（discovery）では、`CLI lint`・`CLI approve` が、申告か数えた大きさが L の spec を ERROR にする。呼び出しの関係でまとまるファイルの塊ごとに spec を分け、分け方を最初の草案と一緒に人に示す。リファクタリングは機能の変更と別の spec にする。分けた spec は、spec ごとに worktree を切って `CLI init` し、まとめて承認して（B の 5）夜の間に 1 本ずつ進める。後の spec は、前の spec のブランチから新しいブランチ（worktree）を切り、「## 制約」に `- 依る spec: <前の spec のディレクトリ名>` を書き、大きさを M 以上にする（承認の時点では試作を作れない）。着手のとき `lineup.py next` が前の spec の先端（マージしたならマージの commit）の上に載せ替え、そこを数える起点にして lint を当て直す（前の spec の変更を数えない。載せ替えられない・lint が通らないなら、その spec を block にして次へ進む）。PR の base は前の spec のブランチにする（stacked PR）。事例では、L のまま 1 本の PR にした spec で、plan のコメントが GitHub に入りきらずにレビューできなくなり、人が分割と stacked PR を指示して約 1 時間の手戻りになった。大きな移行の事例でも、ファイルや塊の単位に分けて検証を回しており、レビューは 400 行を超えると欠陥の見落としが増える
   - **目的の spec（人が 1 回承認し、夜の間に子へ分ける）**: 人が目的の spec（L でよい）を `CLI approve <dir> --by "<返事の要約>" --goal` で承認したら（人の発言の門と、L 以外の lint の ERROR は今までどおり。phase は discovery のままで、実装役の dispatch にも自走にも入らない。`--goal` を付けない approve は L で止まる）、main は次を回す。(1) 親の要件を M 以下の子に分け、子ごとに `CLI init <slug>` し、「## 制約」に `- 親 spec: <親の spec のディレクトリ名>` と `- 親の要件: R<n>、…` を書く（親の要件は全部どれかの子が受け持つ。「## 自走の範囲」の節は親と同じ文にする。違えば承認が ERROR）。子は親と同じ worktree に置き、ブランチを切り替えて回す。(2) 子ごとに B の 1〜3（lint と照合役を含む）を済ませる。(3) 子ごとに fable-advisor → advice-checker を回し（上の「夜の間の承認し直し」の 2〜3 と同じ手順）、`CLI approve <dir> --by "<要約>" --queue --by-advisor` を打つ。子の spec.md の最後の変更の後で、先に承認した子のための相談より後に起動した記録だけが数えられる。通らない子は discovery のまま残し、人の返事を待たずに次の子へ進む。(4) `lineup.py next` で 1 本ずつ回す。(5) 子が全部 done になったら `CLI goal <親の dir>` を打つ（親の要件ごとの子と phase を出す。全部の要件がどれかの子に挙がり、挙げた子が全部 done のときだけ親を done にする。そうでなければ ERROR で、子の無い要件と done でない子を挙げる）。(6) 朝の報告に、子ごとの approved_by と goal の結果を書く。子を作らずに止まると、親は discovery のままなので Stop hook は止めず、朝まで何も回らない
   - 既存の repo では、大きさを `CLI lint` が数えて決める（要件の数だけでは決めない）。数え方と、申告が数えた大きさより小さいときの扱いは `references/existing-repo.md` の「大きさの数え方」に従う（既存の repo では必ず読む）。S と書くなら、承認の前に試作の差分を作り、作ったら `CLI lint` を回し直してから示す（差分が無い S は、lint は NOTE、`CLI approve` は ERROR にする。agent の見積もりだけで S にしないため）。試作を作らないなら M 以上にする。表の変更の目安か要件の数が大きい側に当たるなら、大きい側にする。新しく作る repo では `- 大きさ: <S|M>` を表で決めて書く（L に当たるなら spec を分ける）。大きさの行は 1 行だけ、`- 大きさ: <S|M|L>` の形だけを書く（括弧の注記・全角・2 行は lint が ERROR にする）

   - 機能を足す・変える spec（playbook が feature）では、推奨で埋める草案に、その種類のものに普通は付く機能と既定値を入れる。入れ方は `references/playbooks/feature.md` に従う
4. 作り方の案を 2〜3 個、得るもの・失うものつきで挙げ、推奨を 1 つ示す。案は直し方の 4 段（要らなくする・入力の約束を変える・設計を変える・局所の継ぎ足し）の上の段から先に考え、同じ枠の中の分岐だけを並べない。推奨より上の段の案を退けた理由（その段で目的に届かない訳）は、B の 2 で ADR に `- 直し方:` と `- 退けた:` の行として書く。人が「任せる」と言ったら推奨にする
5. 壁打ちは S なら 1〜2 往復を目安にし、決めきれない点は推奨として spec に書いて承認で確かめる

## B. 合意

1. A の 0 で作った `docs/specs/<日付>-<slug>/` の spec.md を埋める。要件は `- R1: <条件>とき、<対象>は<応答>する。` の形で、確かめられるように書く。「QA の方向性」の表に、要件ごとの確かめ方と合格基準を書く（ブラウザで動くものはブラウザで操作して確かめる。S と新しく作る repo の M は E2E のテストを repo に足さず、ロジックの単体テストと、評価役が C の 3 で行うブラウザの操作を証拠にする。既存の repo の M 以上は、制約が許せば Playwright の E2E を devDependency に入れて既定の証拠にする。計測では、S の implementer の約半分〔約 5 分〕が E2E を書いて直す往復で、main の QA もブラウザで同じ操作をしていた）。時間や状態で変わる要件（落下の tick と固定、タイマーなど）は、「tick ごとに、<条件>なら<遷移>する」という状態遷移の形で書き、QA の方向性では tick を明示的に進める単体テストを求める（計測では、「次の落下のタイミングで固定する」とだけ書いた要件で、実装が古い状態を持ち越し、レビューの high が 3 巡続いた）。「制約」に `- 予算: <分> 分` と、A の 0 で選んだ `- playbook:` を書く
   - 既存の repo では「## 影響範囲」と「## 変えない挙動」も埋める（`CLI lint` が求める）。書き方は `references/existing-repo.md` の「影響範囲と変えない挙動」に従う（既存の repo では必ず読む）
   - 「## 前提」を埋める（`CLI lint` が求める。新しく作る repo では `- 過去:`・`- 前提:` を `なし（<理由>）` にしてよい）。spec が頼っている前提を、`- 目的に届く:`（要件を全部満たしても目的に届かない点）・`- 運用:`（できた後に誰がどの手順で使い・保つか）・`- 普通のやり方:`（同じ種類のものの普通の作り方と出典）・`- 過去:`（変える場所の過去の PR・課題で分かったこと）・`- 前提: <既存の振る舞いの言い切り>` の形で書き、その下に字下げして確かめ方を 1 行に 1 つ、種類を頭に書く（`  - path: <path>:<行>（<補足>）、…`・``  - コマンド: `<cmd>` → <結果>``・`  - URL: <url>`・`  - 未確認: <理由>`。1 つの前提に何行でも書ける。path の後ろの文は補足の括弧に入れ、path はファイルを指す。repo の外のファイルはコマンドか未確認で書く。新しく作る repo では path は使えない）。当たらない行は `なし（<理由>）` と書く（なしで始める行はこの形だけで、理由の中に `）` は書けない）。`- 前提:` は、書く前にコマンドかコードで確かめる（起動の条件・入力の形・権限・既定値など、要件が頼る既存の振る舞いは、思い込みで書かない。計測では、「push のたびに動く」と書いた spec の前提が、workflow の `on:` を読めば違うと分かったのに、本番で動かすまで誰も気づかなかった。ほかにも、マージの後に人が「運用がそれで回るか」「デファクトスタンダードは」「過去の PR を確認して」と問い直した場面が 4 つあった）
   - IaC（Terraform など）で環境を作る・変える要件は、playbook の選びによらず `references/playbooks/iac.md` の「spec を書くとき」に従う（QA の方向性に対象のアカウントでの plan と件数の合格基準を書く。`validate`・`fmt` だけを証拠にしない）。apply は自走で回さない（下の C の安全規則）
   - QA の方向性の表の段の列（`| 要件 | 段 | 確かめ方 | 合格基準 |`）を、`手元で実物`（既定）→ `デプロイ後`（手元では確かめられない要件だけ。`- 手元でできない理由: R<n>（<理由>）` を書く）→ `代役`（実物が手元にもデプロイ後にも無いときだけ。`- 代役の理由: R<n>（<理由>）`）の順で選ぶ（ユーザーの決定「ローカルでQAできる環境があるならそこでQAしてPRつくるで良い　マージしないとQAできないならマージ後にQAするしかない」）。マージの前に本番で一時的な資源（1 回だけ動いて自動で消える schedule など）を作って試す形は `手元で実物` に入れる。本物で確かめられないまま通す要件は `- unverified の承認: R<n>（<理由>）` を書き、承認のときに先頭に示す（無い unverified は `CLI check` が落とす）。デプロイ後の要件が無い spec は、範囲が「マージ・デプロイ・QA まで」なら、デプロイの起動がマージで自動のときはデプロイの成功（落ちたら直すか積む）で終わり、起動がコマンドか「なし（マージした commit で QA）」のときはマージで終わる（`references/after-pr.md` の 3 を通り 4 を通らない、か、3・4 とも通らない）。デプロイの workflow が無い repo（マージしないと QA できないが、マージで動くデプロイも無い）で、デプロイ後の要件がある spec は、`- デプロイの起動: なし（マージした commit で QA）` にし、`- デプロイの確かめ:` を空にする（3 を通らず、マージの記録を起点に 4 へ進む）
   - 外部サービス（AWS・Slack・LLM の API など）を呼ぶ要件か、そのエラーコードや応答で分岐する要件は、playbook の選びによらず `references/playbooks/external-service.md` の「spec を書くとき」に従う（本物で確かめる手順を QA の方向性に書く。同じコードが返るほかの場合を区別する条件を要件に書く）
   - 「## 自走の範囲」の 6 行を埋める（`CLI lint` が求める）。朝の報告の知らせ方を `- 通知:`（デスクトップ・Slack の DM・なし）に、`- AWS の profile:` に、AWS SSO で操作する spec なら profile の名前、使わないなら「なし」を書く（承認の lint が、その profile の SSO が見込みの夜の終わり〔承認から予算とマージ後の予算〕より前に切れるなら ERROR、その 2 倍より前に切れるなら NOTE にする。refresh token の形なら、`aws sts get-caller-identity` が通れば NOTE、通らなければ ERROR にする。寝る前に `aws sso login` し直す）。範囲の既定は「マージ・デプロイ・QA まで」で、狭めるのは人が決めたときだけ。デプロイの起動・確かめ・ロールバックは repo の `.github/workflows` と過去の PR から自分で調べて埋める（デプロイの workflow が無ければ、起動を「なし（マージした commit で QA）」、確かめを空にする）。QA の環境と書き込み先は答えを人しか持たないことが多いので、推奨を添えて 1 つずつ聞く。lint がデプロイの起動の NOTE を出したら、承認のときに人に示す
2. 作り方の選択を ADR にする（`references/adr-template.md`。置き場所は `docs/adr/`。repo の規約があれば従う）
3. `CLI lint <dir>` を通す。ERROR は直す。曖昧な語の NOTE は、確かめられる形に直す。spec の先頭の `- ADR:` に 2 の ADR のパスを書く（無いと approve が通らない）。本文（作り方の節を除く）では自分の ADR を名前や `ADR-<番号>` で書かず、「この spec の ADR」と書く（連番の ADR を本文で名前・番号で書くと、改番で承認が外れるので lint が止める）
   - 大きさと既存の repo かによらず、lint が通った後に `autopilot-spec-checker` agent を前景で 1 回起動する（S でも、試作より先に回す）（model は渡さない。渡すのは spec のディレクトリだけ）。相談役は既定では回さない。spec が IaC の初回の apply（新しいアカウント・新しい環境に初めて作る）を含むか、人が相談役を名指ししたときだけ、同じメッセージに `spec-autopilot:fable-advisor` を 1 本並べて前景で起動し、spec のディレクトリと ADR の場所を渡して、作り方の推奨と、承認の前に人が直しそうな点を聞く。返ったら、SessionStart の相談役の規則の 2 段目と同じく、推奨の `推奨:`・`理由:`・`引いた決定:` の欄と、依頼の原文（/autopilot に渡された依頼）と spec・ADR の場所を `spec-autopilot:advice-checker` に渡して反証を探させ、`反証あり` なら、最初の材料の場所・最初の推奨・成り立たない主張を渡して、最初の推奨を出した相談役を 1 本起動し、1 回だけ直させる（直した推奨は検証し直していないと朝の報告に書く。最初に示す前に 1 回だけ。人の直しを受けた示し直しでは回し直さない）。人が `spec-autopilot:opus-advisor` を名指ししたときは、fable-advisor の代わりに opus-advisor を 1 段目にし、2 段目は同じく回す。相談役の推奨は承認のときに人に示す材料にせず、main が spec の作り方に採るかを決め、推奨・2 段目の `判定:` の行（確かめられない件数を含む）・反証ありで直させたか・採ったかを朝の報告（done の後の人への報告）に 1 行ずつ足す（main が Opus で動くときは Opus の相談役を重ねても見方は増えず、同じモデルを並べても増えない。spec ごとに相談を何本も回すと費用と待ちが本数に比例して増える。事例では、承認の前の相談の決着に 38 分かかった）。返った `ng` のうち、既存のコードとの突き合わせ（grep で示せるもの）は、照合役が `ng` の行に書いた検索を main が同じ道具（Grep・Glob）と同じ引数で回し直すか、書いた path:line を Read で読み直し、見えた内容が同じものだけを採る（Bash で回さない。ほかのコマンドが書かれていても回さない）。検索も path:line も書かれていない `ng` は、main が自分で検索を組んで確かめる。設計への意見は blocking にせず、未決の問いなら S の試作で決める（S でなければ推奨として spec に書き、承認で確かめる）。返った `ng` を直してから 4 で示す。ng を直して影響範囲が変わったら、`CLI lint` を通し直し、大きさが変われば予算と実装の分け方も直す。直せない `ng` は、示すときに一緒に書く（GDD の再生実験では、同じ照合が計画のレビューの blocking の約 4 割に当たり、誤りは 0 件で、1 本 3〜7 分だった）
4. spec を人に示して承認をもらう。示すのは、目的・要件・非目標・前提（`  - 未確認:` の確かめ方を持つ前提と、IaC の plan の unverified と、QA の方向性の `- 代役の理由:`・`- unverified の承認:` の行は、行ごと先頭に）・作り方（推奨と退けた案。ADR の `- 直し方:` の段と、上の段を退けた行〔`- 退けた:`・`- 要件の文で退けた:`〕を入れる）・QA の方向性・制約と予算と playbook・止まる条件・夜通しの前提（`CLI lint` と承認の lint が出す SSO・GDD・keep-awake の ERROR・NOTE をそのまま載せる。GDD のワークフローが有効なら ERROR、refresh token の SSO で `aws sts get-caller-identity` が通らなければ ERROR、keep-awake〔`pmset -g assertions` の PreventUserIdleSystemSleep・PreventSystemSleep〕が効いていない、Mac がバッテリーで動いている〔`pmset -g batt`。蓋を閉じるとバッテリーのまま眠り、keep-awake では止められない。電源につなぎ、蓋を開けておく〕、macOS の更新の自動インストールが有効〔夜に再起動しうる。システムの設定なので人が切る〕なら NOTE にする。keep-awake・バッテリー・macOS の更新・見回り役の NOTE は、見込みの長さ〔予算とマージ後の予算と、まとめて承認したときに前に並ぶ spec の予算とマージ後の予算の合計〕が 60 分を超えるか、予算が読めないか、目的の spec の承認〔`--goal`〕のときだけ出る。1 時間以内の昼の run では出ないので、無いことを人に示さない。SSO と GDD は長さによらず検査する。Claude アプリは更新の再起動で全セッションを止め、自動では再開しないので、寝る前にアプリの更新を済ませておくよう、承認のときに人に示す。試走で権限の自動判定に拒まれた操作が自走の中に無いかは、main が見る。足りないものは寝る前に人が直す。夜の間に切れたものは、残りを park に積む）。**承認は 1 回**。直しの指示なら直して示し直す
5. 承認の返事を受けたら `CLI approve <dir> --by "<返事の要約>"` を実行し、spec・ADR を commit する（`CLI init` が commit しないと知らせた置き場は commit しない）。approve は、spec.md の最後の変更より後に、このセッションで人の発言が記録されているときだけ通る（UserPromptSubmit hook がセッションごとに記録し、transcript の人の発言の行〔origin が human〕で確かめる。同じ repo の別のセッションの発言、background の終わりの知らせ、subagent・別のセッションからの報告は数えない。origin の無い transcript〔headless の `claude -p` など〕では、Claude Code を起動する側が選んだ run を除いて通らない）。返事の後に spec を直したら、もう一度示して返事を受ける。approve の出力に、4 で示していない NOTE（夜の NOTE と SSO の NOTE。前に並ぶ spec の分と `--goal` は approve だけが見るので、ここで初めて出ることがある）があれば、着手・`lineup.py next`・子の分割に進む前に、そのまま人に示す。示したら、人の返事を待たずに進む（直すのは人に任せる。目的の spec は discovery のままで Stop hook が止めないので、ここで turn を終えると朝まで回らない）。
   - **まとめて承認する**（寝る前に複数の spec を承認し、夜の間に順に回す）ときは、spec ごとに B の 1〜4 を済ませ、全部を 1 通で示して承認の返事を 1 回受け（1 通の先頭に、着手の順を番号つきで、依る spec があればその名前と一緒に示す）、示した順に `CLI approve <dir> --by "<返事の要約>" --queue` を実行する（人の発言 1 回が、全部の spec.md の最後の変更より後なら通る。承認の順が着手の順になる。夜通しの前提は、前に並ぶ spec の予算とマージ後の予算を足して確かめる）。queued の spec は予算の時計が動かない。続けて `lineup.py next` で 1 本目に着手する（人の発言は要らない）。1 本が done・block になったら、`lineup.py next` で次の spec に着手する（Stop hook も求める）。依る spec が block なら、後の spec も block になる。依る spec がレビュー待ち（`lineup.py hold`）なら、後の spec はその PR の head の上に着手する。依る spec のある spec は `--queue` でだけ承認でき、承認までの `CLI lint` は init の時点との突き合わせ（前提の path・影響範囲のパスと名前・数えた大きさ）を外して書式だけを見る（前の spec が作るものを書けるように。着手のときに依る spec の先端で当て直す）。承認の後に spec.md を変えた spec は、着手せずに block になる
   - **夜通しの前提（見回り役）**: Claude アプリの再起動（自動更新など）で止まったセッションは、セッションの外の見回り役（`scripts/watch.py`）が 15 分ごとに見て、同じ session id で `claude -p --resume` を起動して起こし直す。入れるのは人で、`python3 <plugin のパス>/scripts/watch.py plist > ~/Library/LaunchAgents/com.spec-autopilot.watch.plist` の後に `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.spec-autopilot.watch.plist` を実行する（入っていなければ、4 の夜の NOTE の条件に当たるとき、承認の前の検査か approve の出力が NOTE で知らせる。止めるときは `launchctl bootout gui/$(id -u)` に同じパスを渡す）。起こすのは、セッションを動かしていた claude のプロセスが死に、transcript が 10 分書かれず、Stop hook がそのとき止める判定になる（自走中の spec が残る、まとめて承認した spec が残る）セッションだけ。claude のプロセスが生きたまま 30 分書かれていない（利用の上限などで止まった）セッションは、二重に書かないよう起こさずに報告する。host の記録が無いセッション（見回り役を入れる前に始まったものなど）も、spec が 30 分書かれていなければ起こさずに報告する。権限の mode が `auto`・`acceptEdits` でなければ起こさずに報告する（headless の default は問いを拒んで続け、Stop hook が止め続けて費用を使う）。進み（spec の phase と repo の HEAD）の無い起こしが 3 回続いても、起こさずに報告する。報告は spec のディレクトリの `watch-report.md` とデスクトップ通知に出し、次の SessionStart が示す（読んでから続ける）。起こされた run は headless で、turn を終えるとプロセスが終わり、background の Bash・agent も消える。待ちは前景で回す（Bash の timeout を付けて `overnight.py await` を繰り返す）

承認の前に、コードを書かない・依存を入れない（S の試作は除く。試作でも依存は入れない）。

## C. 自走

ここからは人に確認しない。implementer と reviewer（評価役）の agent は、Agent の呼び出しに `run_in_background: false` を明示して前景で起動し、返ってきた結果をそのまま使う。background で起動して、ファイル・出力・commit を poll して待たない（shell のループ・sleep・待ちのスクリプトも使わない）（終わりの通知は前景の tool が終わるまで届かず、計測では待ちだけで約 11 分失った）。前景を選べない環境（Claude Desktop など）で結果が `Async agent launched` で返ったら、ファイルを見に行かず、ほかの tool を呼ばずに turn を終える。Stop hook が起こし直しの timer を求めたときだけ、Bash で `sleep 900` を `run_in_background: true` で 1 本張って終える（これは待ちの例外で、poll ではない。Stop hook は、時計の上で生きている timer が 1 本でもあれば止めないので、agent ごとに張らない。待っている agent が残る間は、張った timer を止めない）。turn を終える時点で待っている agent が無ければ（次の agent を起動しない・done・block・wait・人への問いに進むときを含む）、前に張ってある timer を、その turn のうちに TaskStop で止める（止めないと、timer が切れるたびに何もしない turn が出る。事例では合計 21 回出て、同じ問いが最大 3 回続けて表示された。timer の id が分からなければ止めずに進む）。timer の終わりの通知で起きたときに、待っている agent が無ければ、問いや報告を繰り返さずに turn を終える。ほかの Bash は前景で走らせ、長くかかるものは Bash ツールの `timeout` 引数（ミリ秒、最大 600000）を付ける（シェルの `timeout` コマンドは macOS に無い。background の Bash を待つ間は Stop hook が止める。例外は、下の 5 の `gh pr checks --watch` と、`references/after-pr.md` の `overnight.py await` だけ）。「続けてよいか」「どちらにするか」を聞かない。迷ったら spec を根拠に決め、設計を変える決定だけ ADR に書き（spec の「作り方」の節も直してよい）、それ以外は tasks.md の該当タスクの下に `  - メモ: <決めたこと>` の行で残す（tasks.md はタスクの行・見出し・この形のメモの行だけを受け、ほかの行は `CLI check` が落とす）。要件・QA の方向性・制約などほかの節は、承認の後に変えると `CLI check` が落ちる。先頭の `- ADR:` 行の連番の番号は、並行のブランチと番号が重なって改番しても落ちない（改番したら、ADR のファイル名と先頭の行の番号だけを変え、本文は変えない。ディレクトリや slug を変える・ファイルが無いと check が落ちる）。変える必要があるなら「人に戻るとき」に進む。

承認した「## 自走の範囲」の中の操作（範囲がマージ以上ならその PR のマージ、範囲に書いたデプロイの起動と確かめ・ロールバック、QA の書き込み先への書き込み）は、人に確かめずに進める（global の規則の、spec-autopilot の承認による例外）。範囲の外の操作（agent が自分で打つ `terraform apply` など）は実行せず、`overnight.py park` に積んで残りを進める（`references/after-pr.md`）。人がいる間にその場で確かめたいときだけ、`CLI wait <dir> --reason "<確認すること>"` を実行してから人に確かめる。wait の間は Stop hook が止めない。返事を受けたら `CLI resume <dir>` で戻る（返事の記録が無いと通らない）。

1. **計画**: tasks.md に `- [ ] T1: <やること> [R1, R2]` の形でタスクを書く。A の 0 で先頭に写した playbook のタスクは消さずに残し、R の番号が埋まっていることを確かめる。すべての要件をどれかのタスクが受け持つ（QA は 3 の評価役が行うので、タスクにしない）。新しく作る repo の M では、全要件 `[R1, R2, …]` を受け持つタスクを 1 つだけ書く（playbook のタスクがあれば、今のとおり先頭に残す。計測では、新しい repo の M を 2 タスクに分け、実装役が 2 本起動して約 7 分かかった）
2. **実装**: 実装役を起動する直前に、毎回 `NIGHT dispatch <dir> --task T<n>`（受け持たせるタスクの番号）で渡す時点の HEAD を記録する（直しで同じタスクを渡し直すときも打つ）。`NIGHT dispatch` が最後の行に出した名前の agent（既定は `autopilot-implementer`）を起動する（model は渡さない。渡すのは spec のディレクトリと受け持つタスクの番号だけ。S と新しく作る repo の M は全要件を 1 本で、既存の repo の M 以上はタスクごとに 1 本を順に、同じ checkout で並行に書かせない）。main は書かない（既定の実装役は Sonnet 5.5 の effort high。spec-autopilot の repo の 5 本の spec で、effort low より実装の直後のレビューの high が少なかった〔effort high は 4 回だけで、直しの巡のみ〕。計測と数え方は spec-autopilot の repo の docs/adr/2026-11-25-implementer-default-high.md。high が 1 回出ると評価と直しが 1 巡増える。読み方で分かれる点と遊べない不具合は 3 の評価役が拾う）
   - テスト（既存の repo では spec の回帰テストと、足したテスト）が通ったら、ブラウザや CLI で触れるものなら「遊べます: <開き方>。評価を続けます」と 1 行だけ出す（問いではない。人はここから触り始められ、評価と直しは続ける）
3. **評価（QA とレビュー）**: 対象の repo に verify skill があれば（この spec のために作ったものを除く）、評価役の起動の prompt にそのパスを足し、`手元で実物` の確かめはその手順で行わせる（夜の QA の前と、想定外の失敗の後は、その Doctor を通すまで操作させない）。`NIGHT agent <dir> --role review` が出した名前の agent（既定は `autopilot-reviewer`）を起動する（渡すのは spec のディレクトリと差分の base・tip と、既存の repo では起動の前に main が実行した `CLI size <dir> --tip <tip>` の出力の 1 行と、下の観点だけ。評価役はこの「観点 8 の大きさ」で、要件の外の欠陥を探すかを決める）。評価役は、要件ごとに自分の検査スクリプトとヘッドレスのブラウザで動かして確かめ、要件ごとの結果の行と high を返す（計測では、実装した側の QA が pass にした要件の fail を、経緯を知らない評価役が見つけた）
   - 評価役を起動する前に、実装役が返るたびに `NIGHT handoff <dir> --task T<n>`（2 の dispatch と同じ番号）を実行する。handoff は、最後の dispatch がまだ閉じていなければ、その時点から commit が増えたか（その時点が今の HEAD の祖先か）を見る。実装役の「commit した」「[x] にした」を信じない（試走では、どちらも事実と違った）。あわせて、その dispatch の後に、dispatch したセッションで起動した実装役の記録（host が書く meta.json と transcript）を読み、dispatch が出した名前の実装役が、agent 定義の model と effort で動いたかを見る（定義と違う版の model で動いた起動が実際にあった）。通らなければ、出力をそのまま渡して実装役に直させる。起動の記録が合わない（実装役を起動しなかった、別の段の実装役を起動した、model・effort が定義と違う、記録が読めない）ときは、spec の外のファイルを前の dispatch の base に戻して commit し（`git restore --source=<base> --staged --worktree -- . ':(exclude)docs/specs' ':(exclude)docs/adr' ':(exclude).autopilot-qa'`。base は state.json の最後の dispatch の `base`）、`NIGHT dispatch` を打ち直して、出た名前の agent を model を渡さずに起動し直す（戻さないと、起動し直した実装役に作り直すものが無く、commit が無いまま止まる）。`CLAUDE_CODE_SESSION_ID` が無くて確かめられないと言われたときは、実装役には直せないので人に戻す。見るのは起動した実装役の agent・model・effort が定義と合うかだけで、想定するのは事故（model の渡し間違い・effort の継承・段の取り違え）である。handoff で閉じた後に HEAD が動いたときは、増分も起動も見ない。dispatch を打たずに起動した実装役は、起動の入口の hook（`hooks/agent_gate.py`）が dispatch を打つよう deny して止める。閉じた後に main が spec の外に書いたコードは、閉じたときの tip と中身が違うファイル（統合先が変えたファイルを除く）があれば handoff が拒み、そのファイルを閉じた tip に戻して commit するか dispatch から実装役に直させる。rebase・統合先の merge・spec のファイルだけの変更は通す。見分けないのは、統合先も変えたファイルへの main の書き込み（rebase の衝突の解消と区別できない）で、定義と違う model が書いた commit も handoff は取り除かない。取り除くのは上の戻しの手順で、main が spec の外に書いてよいのはこの戻しの commit だけである（ほかは「main は書かない」を 2 のとおり守る）。`CLI review` は、最後の dispatch を今の HEAD で handoff が閉じていないと記録を拒む
   - 返った要件ごとの行を qa.md に写す（やり直したら行を足さず、その要件の行を最新の結果に書き換える）。証拠は評価役の行の欄をそのまま写し、形を書き直さない（`CLI check` が読む形は `templates/qa.md` のコメント）。評価役がブラウザを使えなかった要件は `unverified`（理由を書く）にする。止まる理由にしない
   - 結果を `CLI review <dir> --high none` か `--high R1,R3`（high を受けた要件の番号）で記録する。high は要件ごとの失敗として記録され、失敗か high のあった巡の累計（high も失敗も無い巡では戻さない）で `references/dead-end.md` の段に進む。評価役を起動したら、返るたびに必ず記録する（記録しないと、次の `NIGHT dispatch` と実装役の起動が hook で止まる）。high があれば直し、確かめ直す。評価役が返ったら、直しを起動する前に `find .autopilot-qa -type f | sort | xargs shasum` を実行して出力を控える（配下のファイルを全部見る）。評価役が返るたびに（high none の巡も、`rm -rf .autopilot-qa` の前に）、`find .autopilot-qa -name '*.applied'` で評価役の変異の印が残っていないかを見る。残っていれば、印ごとに同じ名前の patch を `git apply -R --check` で確かめ、通れば `git apply -R` で戻してから印を消し、その巡の結果を使わずに `rm -rf .autopilot-qa` してから評価役を回し直す。通らない印があれば、実装役を起動せずに `CLI block` で人に戻す（印の無い変更は戻さない）。high がすべて `確かめ方: 再実行` なら、評価役を起動せず、main が同じコマンドを回し直す。控えが会話にあり、回し直しが成功して空でなく、出力が控えと一致したときだけ、評価役の `再実行:` のコマンドを Bash で回す（Bash ツールの `timeout` 引数を付ける）。それ以外（控えが無い・失敗・空・不一致。直しで検査スクリプトが変わった場合を含む）は、`rm -rf .autopilot-qa` してから評価役を回し直す（変わったスクリプトを評価役が引き継がず、spec から検査を書き直すため）。終了コードが 0 で、high の要件ごとに `R<n> pass` の行があり、`fail` の行が無ければ通ったとする（どれかが欠けたら、評価役を回し直す）。通れば、high の要件の qa.md の行を、そのコマンドと結果で書き換え、段が手元で実物の要件は、頭に `- commit: <今の HEAD>` を書き、その下に `$ <コマンド>` の行と出力を書いて `evidence/R<n>.txt` を書き直してから、`CLI review <dir> --high none` を記録する（`CLI check` は、要件が最後に high になった巡より後の巡の tip の出力だけを数える）。落ちたら、落ちた要件で `CLI review --high R..` を記録し、出力を指摘として直しに戻る。`確かめ方: 評価役` の high があるか、`再実行: なし` なら、評価役を回し直す（渡すのは前の巡の high と、前の tip から今の tip までの差分）（計測では、直しの後の評価役の巡が 1 本あたり 63〜292 秒で、小さい直しを確かめるために検査を書き直していた）
   - 評価役に差し込む観点は、spec の playbook の「評価役の観点」と、変更の性質で決まる次の 2 つから当たるものだけを選ぶ（main がその場で作らない。名前は `NIGHT lens --name` で夜をまたいで数えるので変えない）: 権限・認証に触る →「権限の境界をまたぐ呼び出し」、本番に直接効く変更 →「失敗したときに本番に何が残るか」。見落としが痛い場面（IaC の初回の apply・権限・認証・本番に直接効く）だけ、別の観点を渡した評価役をもう 1 本、同じメッセージで起動する。評価役の指摘（high も low も）は、main が同じコマンドを回し直して再現したものだけを採る。巡ごとに、観点ごとの指摘の数・再現した数・直した数を `NIGHT lens <dir> --name <観点> --found <n> --reproduced <n> --fixed <n>` で残す（効かない観点を外すため）
   - **段を上げる**: 実装役の段は、要件ごとに CLI が自動で上げる（main は何も呼ばない）。`CLI fail --from impl`（実装役が満たせなかった）を記録した時点で上がり、次のレビューを待たずに上げた段で作り直す。`CLI review` が巡を記録するときも、`references/dead-end.md` の 1（原因を調べる）か 2（作り方を変える）に入った要件を上げる。どちらも、上げた段をまだ渡していなければ上げない（1 巡に 1 段、上げた段で渡し直して満たせなければ同じ巡でももう 1 段）。タスクの段は、受け持つ要件の段の最大で、tasks.md を書き直しても要件に残る。段は Sonnet 5.5 high → Opus medium → Opus xhigh の順に上げ、Opus xhigh で 2 回落ちたら Fable を 1 回だけ試す（Fable で渡した後にその要件の失敗が記録されたら、一番上を超えたとみなす）。一番上でも通らなければ、review・dispatch・agent がその要件だけを挙げて park を言うので、その要件を積む。積んだ要件は渡さず、同じタスクの残りの要件の段で渡し直す。評価役の判定が決まらない（同じ要件で pass と fail が巡ごとに入れ替わる、原因を書けない）ときだけ `NIGHT raise <dir> --role review --reason 判定が決まらない` で評価役を 1 段上げる（Fable は 1 回のレビューで Opus xhigh に戻る）。上げた段と理由、段を上げたタスクの数と上げた後のレビューで通った割合は朝の報告に出る
   - **直し方**: 指摘をそのまま渡して、`NIGHT dispatch` が出した名前の実装役を新しく起動して直させる（S も M 以上も同じ）。implementer が要件を満たせなかったと報告したら `CLI fail <dir> --req R<n> --from impl --evidence "<内容>"` で記録する（TDD の途中の red は記録しない）
   - 評価役が `原因: 差分の外`（認証・権限・backend が無いなど）の fail を返したら、implementer に渡さず、その要件を `overnight.py park` で積んで、ほかの要件を進める（`references/dead-end.md` の 3）。QA の方向性の不足（IaC の plan が無い）の high も同じにする。積んでいない要件が 1 つも進められないときだけ `CLI block` で記録して「人に戻るとき」に進む
   - high none になるまで続け、止めるのは `references/dead-end.md` の梯子と予算の 2 倍だけ。low は直さず PR 本文に書く
4. **完了の検査**: `rm -rf .autopilot-qa` で評価役の検査スクリプトを消し、`CLI check <dir> --stage pr` が通るまで直す（最後のレビューが high none であること、作り方を変える段の要件が残っていないこと、最後のレビューの後にテスト・文書の外のコードが変わっていないことも見る）。「## 自走の範囲」がマージ以上なら、ここでは done にせず、5 で PR を作ってから `references/after-pr.md` のループに進む（`CLI check` の既定は、マージ・デプロイ・実環境の QA の記録が無いと通らない）。範囲が「PR まで」なら、通ったら `CLI done <dir>` を実行し、書き換わった state.json と qa.md・tasks.md を commit する（done が commit しないと知らせたら commit しない）
5. **PR**: 作業ブランチを push して PR を作る。`CLI done` が「大きさが L になった」と NOTE を出したら（自走の途中で差分が育ったときと、合意し直しで L にしたとき）、PR を 1 本にせず、呼び出しの関係でまとまるファイルの塊ごとに commit をブランチに分け、stacked PR にする（1 本目の base は既定のブランチ、2 本目以降は前の PR のブランチ）。各 PR の本文に、マージの順番を書く。本文に、spec と ADR へのリンク（commit しなかったものは、リンクの代わりに要件と作り方の選択の要約）、要件ごとの QA の結果、自分で決めたこと、unverified と直していない low を書く。repo の PR テンプレートがあれば従う（`git ls-files | grep -i -E '(^|/)pull_request_template'` で探す。大文字・小文字と、`.github/`・`docs/`・root・`PULL_REQUEST_TEMPLATE/` の置き場を拾う。グロブで探さない。zsh では一致しないグロブがコマンドごと失敗し、在るテンプレートを見落とした事例が 2 件あった）。範囲がマージ以上なら、PR を作ったら `references/after-pr.md` に進む（CI の待ち・マージ・デプロイ・実環境の QA・朝の報告）
   - 範囲が「PR まで」の既存の repo では、手元で回したのは回帰テストだけなので、PR を作ったら `gh pr checks <PR> --watch` を Bash の `run_in_background: true` で回し、ほかの tool を呼ばずに turn を終えて、終わりの通知で起きる（前景の Bash は 10 分で打ち切られ、長い CI を待てない。done の後なので Stop hook は止めない）。落ちたら、原因が差分の中なら implementer に直させて push し、差分の外なら報告に書く。push や PR を作れない環境では、そのことを報告に書く
6. **報告**: 要件ごとの充足、QA の結果、`CLI done` が出した承認から・着手からの時間、自分で決めたこと、残したこと。次にやる作業の選択肢は付けない（「推奨で」の返事が、頼まれていない low の修正などの作業を始めてしまう）。done の後に返事が来ても、相づち（「OK」「推奨で」など）では作業しない。人がこの PR の直しを頼んだら、下の「done の後に直しを頼まれたとき」に進む

### done の後に直しを頼まれたとき

PR のレビューや人の指摘で直しを頼まれたら、done のまま直さず、自走に戻ってから直す（評価役・qa.md の証拠・`CLI check` を通すため）。CI の失敗の直しだけは、上の 5 のとおり done のまま行う。

- 直しが今の要件の中に収まるなら、spec.md を触らずに、tasks.md に直しのタスクを `- [ ] T<n>: <直すこと> [R<n>]` で足し、`CLI approve <dir> --by "<依頼の要約>"` で自走に戻る。approve は、done の後にこのセッションで人の発言が記録されているときだけ通る
- 要件・QA の方向性・制約を変える直しなら、spec を直し（変えた要件が頼る前提を、B の 1 のとおりコマンドかコードで確かめて前提の節に足すか直す）、`CLI lint` を通し、下の「合意し直しの照合」を回してから変えた点を人に示し、返事を受けてから approve する（spec.md を直すと、その前の発言では approve が通らない。大きさが上がったときも同じ）
- 戻ったら C の 1〜4 をやり直す。5 では PR を作り直さず、同じブランチに push して PR の本文を更新する。ただし `CLI done` が L の NOTE を出し、PR がまだ 1 本なら、C の 5 のとおり塊ごとのブランチに分けて stacked PR にし、元の PR を 1 本目にする。もう分けてあるなら、直した commit をその塊のブランチに積み、分け直さない。マージ済みの PR の直しなら戻らず、`CLI init` で新しい spec にし、「## 制約」に `- 手戻り元: <元の spec のディレクトリ名>` を書く（手戻りの PR の数を `runs.jsonl` で数えるため）（範囲がマージ以上の spec の、done の前の同じ要件の中の直しは、`references/after-pr.md` の 5 のとおり同じ spec のまま直す）
- done の後に人に確認するだけなら、`CLI wait` を使わずにそのまま聞く（done の後は Stop hook が止めない）
- この版より前に作った spec に「## 制約」の `- playbook:` が無いと、`CLI approve` と `lineup.py next` の着手が lint で止まる（着手では block になる）。A の 0 の索引で選んで書き足し、`CLI lint` を通してから人に示して承認を受ける
- この版より前に作った spec に「## 前提」が無いと、spec.md を触らない直しでも `CLI approve` が lint で止まる。前提の節を足して（`- 前提:` は B の 1 のとおりコマンドかコードで確かめて書く）`CLI lint` を通し、下の「合意し直しの照合」を回してから、足した前提を人に示し、返事を受けてから approve する
- state.json を手で書き換えない
- 合意し直しの照合: `autopilot-spec-checker` を前景で 1 回起動し、渡すのは spec のディレクトリと「合意し直し」の語だけにする。実装が進んだ後の作業ツリーには、既存のコードに当てる項目（1〜4・6）を当てられないので、照合役は今のコードに依らない項目（5・7・8・9・10・11）だけを見る。返った `ng` を直してから示す（人に戻るときも同じ）

### 行き詰まり

`references/dead-end.md` に従う。人に聞かずに作り直す。1 つの要件だけが進められないときは、そこに書いたとおり `overnight.py park` で積んでほかを進める。人に戻るのは、どの要件も進められないときだけで、そのときは `CLI block` で記録してから 1 通で示す。

## 中断・引き継ぎ・compaction の後の再開

状態は repo のファイル（spec.md・tasks.md・qa.md・state.json）が正本で、会話の記憶に頼らない。

- 中断: いつ止めてもよい（Esc・利用の上限・PC の終了）。止める前に、書きかけのコードは commit しておく。セッションを開き直したとき（起動・再開）は、最後の活動〔CLI の記録と turn の終わり〕から今までを予算から外す。開いたままのセッションで止めて続けた時間は外れないので、長く止めるときはセッションを開き直す。最後の活動の後に作業していた時間も外れる
- 再開: 同じセッションを開き直す・compaction の後、SessionStart hook が続きのある spec（壁打ち中を含む）の状態（`CLI status <dir>` と同じ）を文脈に入れる。その「残り」を消す段から、C の手順を人に聞かずに続ける（phase が wait なら返事を受けてから `CLI resume`、blocked なら人の返事を待つ）
- Stop hook が止めるのは、自走を引き受けたセッション（approve・resume・adopt を実行したセッション）だけ。fork・同じ repo で開いた別のセッション・/clear の後のセッションは止めない。SessionStart hook は、そうしたセッションには spec の場所と phase だけを出し、続ける指示を出さない
- 別アカウントへの引き継ぎ・/clear の後: 新しいセッションを同じ worktree で開き（/clear の後はそのまま）、人がそのセッションで引き継ぐと言ったら（`/autopilot` の起動を含む）、`CLI adopt <dir>` を実行してから続ける。以後は cwd を移しても Stop hook が止める。人に言われずに adopt しない（fork が止まり続けるため）。hook の文脈が無いときは `CLI status <dir>` を実行して同じ状態を得る

## L. 軽量フロー（人との spec 合意を省く）

入れるのは、受入条件が Issue に書いてあるか、依頼文だけで要件・範囲・完了が決まるときだけ（決まらないなら A・B の合意ありのフローで進める）。範囲がセキュリティ境界まで広がりそうな作業は、初めから合意ありで進める。

1. A の 0 と同じく `CLI init <slug>` で spec を作り、Issue・依頼文から spec.md・ADR を埋めて repo に残す（ADR を commit するなら、名前を `*guardrails*` などの保護の pattern に当たらない名前にする。当たると check が止める）。`- 範囲:` は合意ありの草案と同じく repo の既定にする。`- デプロイの起動:` と `- ロールバック:` はコマンドにしない（人が見ないまま打たないよう approve が断る。マージで自動に動く workflow と revert の PR だけ）。デプロイの workflow が無い repo は、`- デプロイの起動:` を「なし（マージした commit で QA）」にし、マージの後に QA へ進む（打つコマンドは無い）。人の返事は待たない
2. `CLI lint <dir>` を通し、`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/light.py" approve <dir> --source "<Issue の URL か依頼文の要約>"` で自走を始める（人の発言の記録は要らない。判定の起点〔init の時点の commit〕を記録する）
3. ここからは C の自走と同じ（TDD・評価役・QA の証拠・`CLI check --stage pr`・PR、範囲がマージ以上なら `references/after-pr.md` のマージ・QA、`CLI done`）。違いは次の 2 つだけ
   - **止まる条件**: 保護された path に触れたら `CLI check` が通らない。判定は、init の時点の commit（S の試作の commit も入る）から、PR に入りうる変更（起点との HEAD・index・作業ツリーの差と、追っていないファイル）の path だけで行い、照合は git の glob pathspec に任せる（LLM が判断しない。rename は元の名前も見る。spec 自身の置き場は、置き場の名前では当てず、`/` を含まない pattern だけを置き場の下に当てる。承認の前から当たっているなら approve が断る）。既定は `scripts/light.py` の `DEFAULT_PROTECTED`（IaC の `*.tf`・`*.tfvars`・`*.tfstate`・`terraform`・`infra` など、`*guardrails*`、エージェントの規則と設定の `CLAUDE.md`・`AGENTS.md`・`.claude`・`.mcp.json`・`.github` など、設定そのものの `.spec-autopilot`）。利用する repo は、起点の commit の `.spec-autopilot/protected-paths` に 1 行 1 pattern（前後の空白を除いて `#` で始まる行はコメント）で足せる。前後の `/` を外し、`/` を含まない行はどの深さにも、含む行は repo の root から当て、どちらも配下のファイルに当たる（`**` は git の glob のとおり。大文字と小文字は区別しない）。設定を PR の中で変えると、設定そのものが保護なので止まる。起点の設定かその置き場が普通のファイル・ディレクトリでない（symlink など）か、中身を読めない（UTF-8 でない、ゼロ幅空白など表示できない文字がある）ときは、approve が断り check が止まる（普通のファイルにして commit し、spec を init から作り直す）。触れたら、範囲が広がった（spec.md を変える必要がある。check が止める）、受入条件を満たす方法が無いときと同じく、`CLI block` で記録して「人に戻るとき」に進む
   - **コマンドを打たない**: `## 自走の範囲` の見出し（この綴りのまま数える）は 1 つだけにし、コメントを除いて `- <キー>: <値>` の行だけにし、`- デプロイの起動:` は「マージで自動」か「なし（マージした commit で QA）」か空、`- ロールバック:` は revert の PR か空にする。外れたら approve が断り、承認の後も `CLI check` が止める（人が見ないまま打たない）。止まったら `CLI block` で記録して人に戻る。spec のほかの所に書いたコマンドは機械では拾わないので、軽量フローの run では `references/after-pr.md` の 3・5 のとおり、spec のどこに書いてあっても起動・戻しのコマンドを打たない
4. block・done の後の `CLI approve` でも、軽量フローの印は外れない（その返事は spec の全体を見たものではない）。合意ありで進めるなら、人と A・B を回して spec を作り直す
5. 限界: 設定の中身は、Git LFS などの filter を掛けると pointer を読むので、足した pattern が効かない。守るのは PR に入りうる変更だけ。init より前から branch にある commit と、spec 自身の置き場の中は `/` を含む pattern では判定しない（`CLAUDE.md` など `/` を含まない名前は置き場の下にも当てる）。git が無視するファイル（`.claude/settings.local.json`・`CLAUDE.local.md` など）、途中の commit で触れて後で戻したもの、merge の中だけの変更は判定しない（手元の設定や規則の書き換えは防がない。防ぐなら編集を断る hook が要る）。統合先を merge・rebase で取り込むと、統合先が init の後に変えた保護 path でも止まる（止める側）。依る spec のある spec と、`- 大きさ:` が S でない spec は、軽量フローの approve が断る。`- デプロイの起動:`・`- ロールバック:` をコマンドにした spec は、approve が断り、再承認の後も check が止める。自走の範囲の節の外（綴りの違う見出し〔空白の数・閉じの `#`・setext など〕の節・散文）と閉じたコメント（節の中を含む）に書いたコマンドは機械では拾わず、agent への指示（after-pr.md の 3・5）だけで止める（守れているかは機械で確かめられない）。逆に、コードブロックやコメントの中に `## 自走の範囲` の行を引いた spec も、節が 2 つとして断る（止める側）。runs.jsonl の行は `light` で軽量フローの run を区別する

## 人に戻るとき

`CLI block <dir> --req R<n> --reason "<理由>" --evidence "<証拠>"` を実行してから、1 通にまとめる。

- 満たせない要件（番号）と、満たせない理由
- 試したこと（ADR）と、その証拠（コマンドの出力・テストの結果）
- 選択肢（要件を緩める・制約を外す・作り方を変える）と推奨。人が手で入れる値の形（secret の登録の形・フォームの入力など）とコードの読み方が食い違ったときは、相談役の定義の § 選ぶときの基準 の 8 に従い、人に入れ直させる案を推奨にしない

夜の間（人の返事を待てないとき）に、人が一度承認した spec の承認し直しが要るなら、次の手順で通す。初回の承認（discovery・queued）と、`## 自走の範囲` の節を変える承認し直しは、この手順で通らない（人の返事を待つ）。

1. spec を直し、`CLI lint` と上の「合意し直しの照合」を済ませる
2. `spec-autopilot:fable-advisor` を前景で 1 本起動し、承認し直しの相談だと伝えて、spec のディレクトリ・直した点・ADR の場所を渡す。返答の最後に `承認: 可` か `承認: 否` の行が出る
3. 返った推奨を、SessionStart の相談役の規則の 2 段目のとおり `spec-autopilot:advice-checker` に渡して反証を探させる（fable-advisor の起動より後に起動する）。`判定: 反証なし（確かめられない 0 / <n>）` の行が出たときだけ通る
4. `CLI approve <dir> --by "<要約>" --by-advisor` を打つ。2 と 3 の記録が揃っていないか、`承認: 否`・`反証あり`・確かめられない 1 以上なら ERROR になり、spec は blocked のまま残る。通らなければ、直して 2 からやり直さず、そのまま `lineup.py next` で行列の次の spec に進み、朝まで人の返事を待つ
5. 通った巡は、approved_by（`相談役（fable-advisor・advice-checker 反証なし）: <要約>`）を、朝の報告（done の後の人への報告）に 1 行書く。人が朝に読み直す

返事を受けたら spec を直し（この版より前に作った spec なら「## 前提」の節も足す）、変えた要件が頼る前提を、B の 1 のとおりコマンドかコードで確かめて前提の節に足すか直し、`CLI lint` を通し、上の「合意し直しの照合」を回してから、直した点を人に示す。返事を受けてから `CLI approve <dir> --by "<返事の要約>"` をやり直して C に戻る。done の後に直しを頼まれたときは、上の「done の後に直しを頼まれたとき」に従う（block は要らない）。軽量フローの run は、approve をやり直しても軽量フローのまま（保護 path の判定が残る）なので、保護 path に触れて止まったときは、人と A・B を回して spec を作り直すことを選択肢に入れる。
