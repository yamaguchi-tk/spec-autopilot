# ADR: 承認の単位（目的）と PR の単位（子の spec）を分ける

- 日付: 2026-11-26
- 状態: Accepted
- spec: docs/specs/2026-11-26-goal-split

## Context
大きさ L の spec は初回の合意で止まり、人が分けた spec を 1 本ずつ承認する。夜の間に分けた spec は人の承認が無いので回らない。人は「承認の単位とPRの単位を切り離す」「途中の承認はFableでよい」「裏取りはして欲しい」と決めた。

## 選択肢
1. **人は目的の spec を `--goal` で 1 回承認し（phase `split`）、main が分けた子は、親の承認・同じ自走の範囲・相談役 2 段の記録がそろうときだけ `--queue` で承認する。親は、子が親の要件を全部受け持って全部 done になったら done にする**
   - 得るもの: 人の承認は 1 回。子は 1 本ずつ M 以下の PR になる。子の自走の範囲は親を超えない。裏取りが外れない
   - 失うもの: 新しい phase が 1 つ増える。子の要件が親の要件の意味を保つかは、番号と相談役の検証にしか頼れない
2. **L の spec を 1 本のまま承認して回し、PR だけを塊ごとに分ける（done の NOTE の stacked PR）**
   - 失うもの: 1 本の spec の評価と予算が大きくなり、評価役が L の差分を 1 回で読む。A の 3 の L の項を入れた理由（L のままではレビューできない）に戻る
3. **寝る前に人が全部の子を `--queue` でまとめて承認する（コードは変えない）**
   - 失うもの: 寝る前に全部の子の草案・lint・照合を済ませる必要があり、夜の間に分け方を直せない。人の発言「specが複数に分かれてそれぞれ毎に承認する形式も無駄」に合わない

## Decision
1 を選ぶ。子の承認の判定は 2026-11-26-advisor-reapproval の相談役の判定をそのまま使う。

## Consequences
- 人の承認は目的の 1 回で、夜の間に分けた子が回る
- 子を作り忘れても Stop hook は止めない（測ってから足す）。朝の報告の `autopilot.py goal` の結果で人が気づく
- 子は直列で回るので、一晩に入る本数は増えない
- 子は親と同じ worktree に置く（このアプリのセッションは自分の worktree の外に書けない）
