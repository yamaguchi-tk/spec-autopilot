# ADR: spec-autopilot の scripts のリファクタを、指標の前後で合否を決める目的の spec と子 4 本で回す

- 日付: 2026-11-28
- 状態: Accepted
- spec: docs/specs/2026-11-28-metrics-refactor-goal

## Context
前のリファクタ（2026-11-26-split-modules）は行数で分けた。指標で測ると、複雑度と重複は変わらず、import の輪は増え、凝集度は下がった。人は行数以外の指標（複雑さ・凝集度・結合度）で測るよう求め、測る道具（lizard を土台にした skill）を repo の外に作った。

## 選択肢
1. 目的の spec に指標ごとの目標を書き、playbook・複雑度・import の輪・凝集度の子を順に回す: 合否が数字で決まり、子ごとに M に収まる
2. 1 本の spec で、目安を超えた関数とモジュールを全部直す: 子に分けないので速いが、L を 1 本の PR にすることになり、レビューできない
3. 測る道具を repo に入れ、check が指標の悪化で止める: 指標が仕組みに組み込まれるが、道具の依存（lizard）が plugin を入れる全員に要る

## Decision
1 を選ぶ。目標は、複雑度 20 を超える関数を半分以下（18 → 9 以下）、deploy.py の LCOM4 を 2 以下、import の輪を 0 にする。子は R1 → R2 → R4 → R3 の順にする（deploy.py の分け方が import の向きで決まるため）。指標は repo の外の道具で測り、repo には playbook の合格基準の形だけを入れる。

- 直し方: 設計を変える
- 退けた: 要らなくする（行を足す改善は今後も続くので、複雑な関数と import の輪は使い続ける。消せない）
- 退けた: 入力の約束を変える（CLI の引数・spec の書式を変えても、関数の中の分岐の数とモジュールの依存は減らない）

## Consequences
- 子ごとに、前後の指標と「移しただけでない」ことで合否が決まる
- 指標は道具の近似の値で、ほかの道具とは一致しない。前後を同じ道具で比べる
- 測る道具の無い人は、playbook の合格基準を自分の道具で満たす
- 3 は、指標で止める仕組みが要ると観測してから、別の spec で決める
