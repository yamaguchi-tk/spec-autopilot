# ADR: 作り直しの入口で、直し方の段と上の段を退けた理由を CLI が求める

- 日付: 2026-11-25
- 状態: Accepted
- spec: docs/specs/2026-11-25-fix-order-park

## Context
handoff-after-close の R3 の作り直しは、根本の案を「要件が変わる」として退け、局所の直しを続けた。dead-end.md の 2 は「要件を緩める案は挙げない」とだけ言い、要件の文に締め出された案の行き先が無かった。requirement-how-check の R1 では、継ぎ足しの直しの後に作り直しになった。どちらも、どの段の直しを選び、上の段をなぜ退けたかが記録に残らず、誰も確かめられなかった。

## 選択肢
1. **rework が ADR の `- 直し方:`・`- 退けた:`・`- 要件の文で退けた:` の行を読み、足りなければ拒む。要件の文で退けたなら park のコマンドを出す**
   - 得るもの: 段の選択が記録に残り、要件の文に締め出された案が朝の報告で人に届く。今の rework の入口に乗る
   - 失うもの: 行の形しか見ないので、中身の無い理由も通る
2. **dead-end.md と adr-template.md に段の順位を書くだけにする**
   - 得るもの: 変更が小さい
   - 失うもの: 「要件を緩める案は挙げない」も文で、handoff-after-close では効かなかった。同じ文の継ぎ足しになる
3. **作り直しのときに、agent が要件の作り方の部分を書き換えてよいとする**
   - 失うもの: 承認の境界を、agent の自己申告で動かすことになる

## Decision
1 を選ぶ。段の並びは pstack の fix-root-causes（最初に誤った場所で直し、ガードは守る状態が正しいときだけ直しとみなす）に合わせ、上から要らなくする・入力の約束を変える・設計を変える・局所の継ぎ足しとする。要件の文を変える判断は、承認の境界なので人に戻す（park）。

## Consequences
- 作り直しの ADR に 1〜4 行が増える
- 要件の文で退けた要件は、作り直しの回数を使わずに park に積まれ、check はその要件に作り直しを求めない
- 形だけ埋めた理由は止められない。評価役と朝の報告で読む
