# ADR: 要件の high で、入力の種類の表を直しの入口と出口の条件にする

- 日付: 2026-11-25
- 状態: Superseded（表のファイルの形は docs/adr/2026-11-25-input-kinds-file-is-one-table.md。置き場と止める場所はこの ADR のまま）
- spec: docs/specs/2026-11-25-input-kinds-table

## Context
docs/specs/2026-11-23-handoff-after-close の R3 では、レビューの high が 4 巡続いた。巡ごとに、指摘された spec のパスの形を 1 つずつ足す直しだった。実装役の定義には「指摘の入力は例として扱い、同じ判定を通る入力の全部で成り立つように直す」という文があるが、文だけでは効かなかった。落ちた入力のほかの種類を、誰も書き出さないまま直しに渡していた。

## 選択肢
1. **評価役が high のときに `inputs/R<n>.md` に入力の種類の表を書き、dispatch が表を、handoff が行ごとのテストを、check が fail の行を見る**
   - 得るもの: 種類を挙げるのは、落ちた入力を見つけた評価役になる。直しの入口と出口で CLI が機械的に止める。今の dispatch・handoff・check の流れに乗る
   - 失うもの: 行の数と形しか見ないので、種類が足りない表も通る。high の巡ごとに評価役の書く量が増える
2. **実装役の定義の文を強める（「同じ判定を通る入力を 3 つ以上テストにする」など）**
   - 得るもの: 変更が小さい
   - 失うもの: 今ある文と同じ形の継ぎ足しで、handoff-after-close では効かなかった
3. **`autopilot.py review --high` が表を求める**
   - 得るもの: high を記録する時点で止まる
   - 失うもの: autopilot.py は 1498 行で、利用者の規則の目安（1500 行）を超えやすい。表が無いまま直しに入るのを止めるのは dispatch でも同じ

## Decision
1 を選ぶ。止める場所は、直しを渡す dispatch（表があるか）、直しを閉じる handoff（行ごとのテストがあるか）、完了の check（fail の行が残っていないか）とする。

## Consequences
- high の巡で、評価役が表を書く手間が増える
- high の後の直しは、表の行ごとにテストを書かないと閉じない
- 種類が足りない表は止められない。次の巡の評価役が読んで行を足す
