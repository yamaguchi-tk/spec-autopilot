# ADR: ふわっとした依頼の壁打ちを /spec に分け、速い往復と具体例で完了条件に熟成させる

- 日付: 2026-11-28
- 状態: Accepted
- spec: docs/specs/2026-11-28-spec-command

## Context
`/autopilot` は最初の返事から lint を通した草案を出し、示す前に照合役を回す。往復を減らす設計だったが、2026-11-20〜28 の 33 セッションで、最初の返事まで中央値 8.9 分、agent を回した往復は中央値 11 分になった（回さない往復は 0.4 分）。人は「一発で正解を出さなくても良いから反応良く壁打ちして熟成させたい」「要件自体もふわっとしたもの」と言った。

目的に届かなかった事例 22 件のうち 6〜7 件は、目的そのものの確かめ方が spec に無かった。調査の記憶は「覚えて賢くなる」を完了条件にしないまま、要件を全部満たして目的に届かなかった。

## 選択肢
1. 要らなくする: 今の A の 2 のまま、人に速く返すよう頼むだけ。得るもの: 何も作らない。失うもの: 最初の返事の前に lint と照合役を回す決まりが残り、待ちが変わらない
2. 入力の約束を変える: 依頼に要件と完了条件が明示されていれば今の道、無ければ壁打ちの道に分け、壁打ちの道では往復で agent・CLI を回さず、「固めて」の 1 回だけ lint と照合役を回す。壁打ちの手順は `/spec` に 1 か所で書き、`/autopilot` の A からも使う。目的の確かめは `- 目的の確かめ:` の 1 行で、要件の QA に寄せる。得るもの: 往復が agent を回さない速さに近づき、承認の門のコードを変えない。失うもの: 「固めて」と「OK」で人の返事が 1 回増えうる。照合役の指摘が固めた後に初めて出る
3. 設計を変える: 2 に加えて、「固めて」の後の照合役の ng が 0 件なら、「固めて」を承認として数える（approve の起点を変える）。得るもの: 人の返事が 1 回減る。失うもの: 人の発言の門を変え、最終の中身を人が見ないまま承認する
4. 局所の継ぎ足し: 今の A の 2 に「速く返す」の注意を足す。得るもの: 文の 1 行。失うもの: 1 と同じく待ちの原因が残る

目的の確かめの持ち方:
- a. 評価役に `目的` の行を返させ、qa.md と check を `R<n>` の外の行に広げる。失うもの: qa.md の読み取りと check の変更が要る
- b. `- 目的の確かめ: R<n>` で要件の 1 つを名指しし、その要件の QA で確かめる（採る）。マージ後にしか測れないなら `- 目的の確かめ: マージ後（<確かめ方>）`。得るもの: 今の qa.md と check のまま確かめられる

## Decision
2 を採る（R1〜R5）。人の決定「要件と完了条件が明示されない指示はふわっとした話で良い」「ふわっとした話はmainの判断に任せたい」に、冒頭の判断の基準をそのまま合わせる。起動条件を広く取り、冒頭で依頼の中身を判断する形は superpowers の brainstorming に倣う（人の発言「起動条件が良く出来ている」）。目的の確かめは b（R6）。

- 直し方: 入力の約束を変える
- 退けた: 要らなくする（最初の返事の前に lint と照合役を回す決まりが残り、人の言う「往復で何分も待たされる」に届かない）

## Consequences
- 壁打ちの往復では、main は Read・Grep・Glob でコードを読むだけになり、agent と CLI を回さない
- 「固めて」の後に初めて照合役の ng が出るので、示し直しが 1 回増えることがある
- 今ある spec を承認し直すときも、`- 目的の確かめ:` の行が無ければ lint が止める（前提の節を足したときと同じく、行を足して示し直す）
- 完了条件（往復の中央値 1 分以下、最初の返事まで 1 分以内）は、マージ後の 5 本の run の transcript で測り直す
