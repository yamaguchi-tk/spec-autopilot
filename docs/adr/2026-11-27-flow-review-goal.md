# ADR: 夜の自走で観測した 5 つの詰まりを、目的の spec 1 本と、要件ごとの子 5 本で直す

- 日付: 2026-11-27
- 状態: Accepted
- spec: docs/specs/2026-11-27-flow-review-goal

## Context
split-modules の run と、2026-11-20〜27 の auto mode の拒否の集計（本物の拒否 48 件・31 セッション）で、5 つの詰まりを観測した。承認し直しの後の handoff、拒否の後の扱い、評価の記録の tip の照合、L の NOTE の時期、目的の spec の goal の読み方である。案は直前のセッションで相談役と検証役が確かめ（反証なし）、人は「まとめて承認」と返した。5 つは触るファイルがほぼ重ならないが、どれも hook か判定を変えるので、repo の規則で /autopilot で回す。

## 選択肢
1. 目的の spec を 1 回承認し、要件ごとに子 5 本を順に回す: 人の承認は 1 回。子は PR が 1 本ずつで小さく、どれかが詰まっても残りが進む。子の承認に相談役と検証役が要る
2. 5 本の spec を今まとめて書き、`--queue` で承認する: 人の承認は 1 回だが、5 本の spec を承認の前に全部書いて照合する。後の子は前の子のマージで行番号が変わり、承認の後に spec を直すことになる
3. 1 本の spec・1 本の PR にする: 差分が 400 行を超えて L になり、初回の合意で lint が止める
4. 子の承認で spec を直したとき、相談役と検証役のどちらか一方で済ませる: 子の承認が速くなるが、承認の門を緩める

## Decision
1 を選ぶ。子は R1 → R2 → R3 → R4 → R5 の順に回す（承認し直しの戻しが最も人の手を要したので先頭、goal の読み方は最後の子の閉じ方にも効くので最後）。4 は退ける。

R1 は、reapproval-carry-merge の spec の R3（実装役の dispatch と handoff は新しい巡で数え直す）を、前の巡の最後の dispatch が handoff で閉じていて spec の外が同じ場合に限って覆す。数え直す決定は、コードを変えた巡で前の巡の実装の記録を使わないためのものだった。spec の外が前の handoff の tip と同じなら、数え直しても実装役に作るものが無く、handoff は commit の無いことで止まり、戻す手順は auto mode に拒まれて人の手が要った。レビュー・QA・park は今までどおり数え直すので、評価役は新しい巡で確かめる。

## Consequences
- 子ごとに PR が 1 本、版数の patch が 1 つずつ上がる
- R5 が入るまでは、goal が子の done を読めない詰まりが、この目的の spec 自身の閉じ方にも起きる。前の子の done の state は、R5 の子の中で読めるようにするか、子のブランチの commit を取り込んでから goal を打つ
- R2 は文での指示で、拒否の後に別の形を試すことを機械では止めない
