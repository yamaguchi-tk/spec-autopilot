# ADR: 新しい作業の土台を GDD から spec-autopilot（成果物と機械の検査で固める軽いハーネス）に替える

- **日付**: 2026-11-15
- **状態**: Accepted（2026-11-15、ユーザー「承認する」「自前で作る」）
- **spec**: `docs/specs/2026-11-15-spec-autopilot.md`

## Context

依頼（2026-11-15）は「要件・作り方・QA の方向性・制約を合意したら QA まで自走する。HITL は要件が満たせないときだけ。袋小路も自律で解く。速さと費用の両立。テトリスで 1 時間は使えない。要件は人と壁打ちで詰める。ADR と Specs は欲しい」。追加の発言は「superpowers よりもかっちりしたハーネスを作りたかった」「KDDI アジャイル開発センターとかの事例も調べてみて」。

実測（2026-11-15）:

1. **テトリス（落ち物パズル）を GDD で作った例**: 5 時間 18 分たっても要件整理（requirements-gating）を終えず、コードは 0 行。待ちが 3 時間 50 分（hook の不具合と root checkout の取り合い）、手順の重さが 85 分以上。人の返事 3 回はすべて「推奨で」で、そのたびに Opus の reviewer 3 本が 10〜15 分かけて全範囲を読み直していた（tetris-dev-optimization セッションの分析。PR #668 で一部を直した後の見込みでも、最初の区切りだけで約 27 分）
2. **同じ遊べる版を、合意済みの仕様から素の Claude Code（Sonnet の subagent）で作った例**: subagent の走行時間（duration_ms）で 1 分 49 秒で、要件をすべて満たす実装と単体テスト 22 本（全部通過）と commit までできた（このセッションの実測。scratchpad の bench-plain。git の時刻差 4 分 13 秒は、その前に週の上限で失敗した headless の 2 回を含む）。QA は node での読み込みまでで、ブラウザでの操作と、合意の前の壁打ちの時間は測っていない
3. **直近 2 週間の GDD**（2026-11-01〜14、正式 GDD 19 件。scratchpad の gdd-measure の script で集計、費用は Opus 換算の概算）: 着手から PR までの中央値は 44.0 時間（p90 67.7 時間）で、その 75% は人の返事待ち（夜間を含む）。費用 $6,588 の 58% は gate の subagent で、要件と設計の gate だけで 37%。上限停止は 33 回（要件 28・設計 5）。HITL への返事 144 件のうち 41〜49% は「OK」「推奨で」だけだった。変更 300 行未満のタスク（3 件）で、コードを書く時間は稼働の 0〜4%
4. **spec-autopilot で同じ種類のタスクを通した例**（このセッション。scratchpad の bench-autopilot。人の返事は「推奨で OK」を事前に与え、main の役を Sonnet の subagent に任せた）: 承認から完了（`autopilot.py done`）まで 6.8 分、subagent の走行は 7.9 分。テスト 24 本が通り、最後の Opus のレビューが実害のバグ 1 件（キーのリピートでピースが止まる）を見つけて直した。実ブラウザでの描画は、ローカルのサーバーの起動が権限で拒否されて unverified
5. **GDD の規模**: テストを除いて約 7 万行（hooks 2.9 万・scripts 1.6 万・references 1.2 万・skills 1 万）、テスト約 10 万行。hook は 29 個（PreToolUse 17）、Stop hook だけで 1,383 行
6. **GDD を直す費用**: 2026-10-15〜11-15 にマージした coding-agent-plugins の PR 166 本のうち 164 本が GDD 自身の修正（+44,000 行／−10,800 行）。週次の分析（10-27）では plugins の 1 PR の費用の中央値が $27、作業時間 1.4 時間。後続 PR の連鎖が週の PR の 47%
7. **他の候補と事例**（2026-11-15 の調査。README・公式 docs・記事）
   - superpowers v7: 壁打ちと「合意の後は聞かない」原則はあるが、文の指示だけで、worktree の同意・計画のレビュー・ブランチ処理の 3 択など人に聞く場面が残る（相談役 2 本の指摘）。ADR・QA の方針・完了の機械検査は無い
   - KDDI アジャイル開発センター: 2025-09 に仕様駆動を導入し、Kiro から cc-sdd（Claude Code 上の Kiro 方式）へ。設計と開発の配分が 2:8 から 8:2 に。うまくいかなかった点は、仕様と実装の整合の維持、設計を細かく書きすぎると遅い、AI が頼まれていない機能を足す
   - cc-sdd: EARS の受け入れ条件に ID、承認後はタスクごとに新しい実装者で TDD と独立レビュー、実装後に validate-impl で網羅を検査。手動のチェックリストでは AI がタスクを飛ばして完了と報告した実例がある。承認は要件・設計・タスクの 3 回
   - AWS AI-DLC: 工程の深さをタスクの複雑さで変える。判断を decision-log に残し、追跡性（traceability.json）を出す
   - NTT データの個人の事例: hook で即止めるのは機械で判定できるものだけ、残りは警告。承認の遅さが全体の律速
   - ADR を作る機能、QA の方針を合意する専用の成果物、「要件を満たせないときだけ人に戻る」の規定を持つ候補は無かった
8. **最近のハーネスの傾向**（2026-11-15 の調査。Anthropic の長時間エージェントのハーネスの記事 2 本、Claude Code の /goal、Ralph のループ、LayerX・every・メルカリの記事）
   - 進み具合と完了の条件をファイルに置き、終わりの判定は機械の検査で行う。モデルの自己申告で終えない
   - 実際に動かして確かめる（ブラウザの E2E を証拠にする）。レビュアーにも実行させる
   - 並行に書かせるより、隔離（worktree）と直列が事故が少ない
   - ハーネスの部品はモデルの弱さを補う仮定なので、モデルが変わるたびに外して測り、要らなくなったものを消す
   - Stop hook による続行は Claude Code 側に連続 block の上限（公式の記述で 8 回。GDD の観測では最大 9 回）があり、上限に当たると hook が上書きされる

## 選択肢

1. **GDD を直し続ける**: 1 か月 164 本直しても、テトリスの最初の区切りに 27 分かかる見込み。直すたびに規則が増え、直す作業そのものが主な費用になっている
2. **superpowers＋文の上書き**: 軽いが、上書きは文の指示なので、superpowers の強い文（「Wait for their answer」）に従って止まる場面が残る。完了の検査も文に頼る。「かっちり」に届かない
3. **cc-sdd をそのまま使う**: 事例（KAG）があり型も整っている。承認が 3 回、ADR と QA の方針の合意が無い、承認の後に止まらない仕組み（Stop hook）が無い
4. **自前の軽いハーネス（spec-autopilot。推奨）**: かっちりさを「成果物の型」と「機械の検査」で作り、LLM の多段レビューと人への確認では作らない

## Decision

選択肢 4 を採る。事例から採ったものと、GDD から外したものは次のとおり。

- 採る: 要件に ID を付け、曖昧な語を機械で警告する（cc-sdd）。承認は 1 回にまとめる（KAG・NTT データの律速の指摘）。承認後はタスクごとに新しい実装者で TDD（cc-sdd。ただし S のレビューの high と QA の fail は、spec・指摘を文脈に持つ main が、再現の単体テストを先に書いて直す。計測では、新しい実装者の直しは読み直しで 1 巡 4〜9 分かかった）。要件→タスク→QA の証拠の対応を script で検査する（cc-sdd の validate-impl、AI-DLC の traceability）。止めるのは機械で判定できるときだけ（NTT データ）。深さを大きさで変える（AI-DLC）。判断を ADR に残す（AI-DLC の decision-log）。承認の前に ADR の実在を検査する。ブラウザでの実際の操作を証拠にし（M 以上は E2E を既定にする。S は計測で E2E を書く往復が実装の約半分だったので、main の QA の操作で代える）、reviewer は自分でテストを回して high に実行の証拠を添える。worktree と直列の実装（いずれも 8 の傾向）。Stop hook の連続 block の上限は Claude Code に任せ、自前では数えない（自前の数えは放す経路を増やし、結果は Claude Code の上限と同じだったため）
- 外す: LLM の reviewer の多段 gate（GDD のテトリスの損失の主因）、承認前の spec の LLM レビュー（ユーザーの返事は「必要で無ければ残さなくて良い」。必要かどうかは未測で、速さを優先して外した。確かめられない要件や要件どうしの矛盾による手戻りが出るかを最初の 5 タスクで読み、出たら戻す）、人への中間確認、hook による多数の強制（29 個 → Stop hook 1 個）、相談役の並行の相談
- 品質の担保: TDD、最後の独立レビュー（high だけ直し、high none まで回し直す）。行き詰まりの梯子（同じ要件の失敗のある巡が 2 巡続いたら原因を調べ、3 巡続いたら作り方を変えて新しい ADR。失敗も high も無い巡で 0 に戻す、作り直しは要件ごとに 2 回まで、その後は人へ）を、レビューの high・QA の fail・実装の満たせなかった報告を要件ごとに数えて `check` で強制する、QA の実行と証拠、`autopilot.py check` の機械検査、Stop hook（検査が通るまで turn を終えさせない。予算の 2 倍で放す）
- 費用: 実装は Sonnet、最後のレビューだけ Opus（agent の定義で固定）
- GDD は消さない。新しい作業の入口を `/autopilot` にし、GDD で進行中のタスクはそのまま GDD で終える

## Consequences

- GDD の hook は、plugin を有効にしている間は全セッションで動き続ける。GDD が active な repo では、`/autopilot` は準備の段で止まって聞く。GDD の plugin を無効にするかはユーザーが決める（settings の変更はすぐ効くので、このセッションでは変えない）
- GDD を直している他のセッションは、GDD を使い続ける作業（GDD で進行中のタスク）のためには意味が残る。新しい作業を `/autopilot` に移すなら、GDD の改善の新しい連鎖は止めてよい
- spec-autopilot が持たないもの: done guard・merge gate などの hook の強制、要件・設計段の LLM レビュー。設計段の誤りは、最後のレビューと QA と check で拾う前提になる
- 部品ごとに置いた理由は次のとおりで、モデルを替えるたびに 1 つずつ外して通しの計測を回し、承認からの分数と手戻りが悪くならなければ消す: Stop hook（自己申告で終える）、check（タスクの飛ばし）、最後のレビュー（実害のバグ。計測で 1 件）、人の発言の時刻の検査（自己承認）、行き詰まりの梯子の数え（compaction で回数が落ちる・レビューの high が残ったまま完了する）
- 効果は、通しの計測 1 回（このセッション）と、最初の 5 タスクで読む。読むもの: `autopilot.py done` の「承認からの分数」、人に戻った回数と理由（state.json の blocked）、マージ後の手戻りの PR の数。S の予算 30 分を超えることが続くか、手戻りが GDD の週次の値（PR の約 2 割）より多ければ、足りない部分だけを足す
