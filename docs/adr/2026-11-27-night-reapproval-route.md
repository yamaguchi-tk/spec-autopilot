# ADR: block の後は、時刻によらず相談役の承認し直しを先に試す

- 日付: 2026-11-27
- 状態: Accepted
- spec: docs/specs/2026-11-27-night-reapproval-route

## Context
夜の承認し直し（`approve --by-advisor`）は入ってから 3 日で 0 回しか使われず、夜の間に要件の文を直す必要で block した spec が朝まで約 10 時間止まった。block の出力と status の行は人の返事を待つ道だけを示し、command の本文は承認し直しを「夜の間（人の返事を待てないとき）」に限っている。その spec のセッションは、相談役を block より前に回したので、門に数えられなかった。人は前に「途中の承認はFableでよい」「裏取りはして欲しい」と決めている。

## 選択肢
1. **「夜の間か」を決めず、block の後はいつも承認し直しを先に試す。通らないときだけ人に 1 通で示す**
   - 得るもの: 判定のコードが要らない。夜か昼かを main が読み違える余地が無い。人の決定（途中の承認は Fable でよい）に合う
   - 失うもの: 人がいる昼でも、要件の文の直しを相談役が承認する（人は朝の報告か、その場の出力で読み直す）
2. **最後の人の発言からの時間（例: 30 分）で「夜の間」を機械で決め、その間だけ出力に承認し直しを出す**
   - 得るもの: 人がいるときは今までどおり人が承認する
   - 失うもの: transcript を読む判定が増える（autopilot.py は 1500 行を超えていて、足せない）。閾値の根拠が無い。headless の run は人の発言が無いので常に夜になり、結局 1 に近い
3. **出力を変えず、command の本文だけを直す**
   - 失うもの: 観測した失敗は、本文の夜の手順があるのに使われなかったもの。block の直後に main が読む出力が人の道だけを示す限り、同じ失敗が残る

## Decision
1 を選ぶ。門（advisor_approval.py）は変えない。

## Consequences
- block の後に、spec の直しと相談役 2 本の起動が毎回入る（1 回あたり数分）
- 相談役が否と言うか、反証が出た承認し直しは、今までどおり人の返事まで止まる
- main が出力を読んでも道を選ばない事故は止められない。使用の回数が 0 のままなら、Stop hook で強制する spec を別に出す
